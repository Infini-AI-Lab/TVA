- **L161** ACCEPT — The exclusion is stated on the source (`docs/SEMANTICS.md` "Atomics", `docs/exclusions.md`, `Compiler.Faithful` scope 12) and is wide enough. Outside it, every cell two operations share is reached only by atomics whose results are unused, and `Step.defer` (nested, through picks and other atomics) can then perform them in any order. Results used on cells no other operation reaches return deterministic values whose timing nobody can observe, and plain cross-program accesses race. So no device order is missing. My `work/atomic_variants.py` (100 runs each) confirms this. The same call run again in a loop, and a result used only in an address, each gave values outside the semantics in 100/100, and both are excluded. With the second call's result unused, 100/100 were outside, which is why the same-program case must cover unused second operations. With `tl.debug_barrier()` between, 0/100: wider than needed, and sound. Stream-K, the histogram and the LoRA shrink discard their results and stay in scope. On the Lean side, I read the proof of `crosswarp_excluded`: it reaches program 0's lane-0 `rmw` of `Y[0]`, whose continuation's store differs at lane 0, and program 1's `rmw` of `Y[0]`. Its axioms are the standard three (`work/axioms.lean`). `work/discarded.lean` proves that a discarded result's continuation is equal for every old value, so the predicate is not satisfied trivially.
- **L162** ACCEPT — Both readings drop a value only when nothing that runs on the device reads it. The stricter fallback is stated, and L161 reads "uses" the same way.
- **L163** ACCEPT — It is consistent with `DivFull`, because the fused result rounds an exact `p` that rounds to the quotient the division alone gives, and that is `AddRel` at the quotient `tl.div` picks. `tl.sigmoid` and `tl.softmax` are inlined Triton code ending in `/` or `fdiv`. Counting the IEEE `softmax(ieee_rounding=True)` or `tl.where` forms as products is harmless, since the fusable forms contain the IEEE ones. No library lemma composes `tl.div` with an addition (grep of `lean/TVA/Lemmas`). I re-ran `evidence/div-fusion` and got the same output. Other operations are not fused into a following add (`work/math_fusion.py`, `work/frem_fusion.py`: `exp`, `exp2`, `log`, `log2`, `sqrt`, `rsqrt`, `sin`, `cos`, `erf`, `sqrt_rn`, `div_rn`, float `%`; 0 results off the IEEE sum, final `FADD`).
- **L164** REOPEN — The new sentence is false: "at most one of which runs per lane and neither with a NaN operand … or none" (`docs/SEMANTICS.md:845-847`; `evidence/relaxed-atomics/README.md:57-58`). The predicate is `_signbit(val)` and its negation (`triton-3.8.0-semantic.py:1326-1333`), so exactly one `atom` runs per enabled lane, NaN operands included. On the H200, `atomic_max(1.0, +NaN)` stored `0x7fc00000` (`work/fmax_nan_mem.py`). `work/fmax_nan.py` checked 256 pairs of special values each for `max` and `min`: every returned value was the old bit pattern and every new value was inside `fBound`. Fix: "exactly one per enabled lane: `max.s32` when the operand's sign bit is clear, `min.u32` when it is set".
