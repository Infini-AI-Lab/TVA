## New issues

- **NEW** gap — The proof kit lacks rules for three model operations. `tl.convert` has none (`TVA.Lang.Promote`: integer `.to(…)`, implicit promotions and the `int1` condition of `tl.where`, which TRANSCRIPTION's worked patterns write as `← tl.convert …`). It is an `env` then a `pick`, so each kernel must build the result tensor by choice. `tl.sum0c` has none, though `safe_sum1c` exists. `tl.store1` has none, against LIBRARY.md's "one rule per operation"; it is `tl.store` of the scalar tensors by `rfl`. Fix: add to `lean/TVA/Lemmas/Ops.lean` `safe_convert` (premise `∀ i, ∃ r, ConvRel E.P d d' (x.get i) r`; continuation for every `r` with `∀ i, ConvRel E.P d d' (x.get i) (r.get i)`) and `safe_sum0c` (as `safe_sum1c`), both proved as stated in work/MissingRules.lean. Add `safe_store1`, or say in the module docstring that `safe_store` applies to `tl.store1`. List them in LIBRARY.md's `Ops` row.
- **NEW** wording — Some lemma docstrings say what their statements do not, so a prover could misread them. (1) Three places still call `u·|y| + η` "half an ulp", which the round meant to remove: the module docstrings of `lean/TVA/Lemmas/FusedErr.lean` (lines 11-12, `RoundsTo.err`) and `lean/TVA/Lemmas/Consistency.lean` (lines 44-45), and `base` in `lean/TVA/Lemmas/Sm90.lean:38`. Say "one rounding's bound". (2) `ofRat_err` (`lean/TVA/Lemmas/FloatErr.lean:100`) calls `FloatV.ofRat` "`tl` constants of exact values". The constant Triton builds for a Python number is `litF32`/`litF16`/`litBF16`/`litF8` (SEMANTICS "Constants"), so say "the nearest float to an exact rational". (3) `lean/TVA/Lemmas/Shared.lean:23` says an `AtomicStep` records the update. It records the cell and the old and new values, not the operand (as `TVA.Lemmas.SharedAcc` says). (4) LIBRARY.md's `Consistency` row says `FloatV.exists_nearest` holds "from any real". It needs `|y| ≤ maxVal`.
