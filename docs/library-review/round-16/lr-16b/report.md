## New issues

- **NEW** soundness — The library does not say what a claim covers when the launch is captured into a CUDA graph, and what it does say is false there. Where it is: `TVA.Claim`, `Launch.Valid`'s docstring, compiler-faithful.md ("What it says"), SEMANTICS "Launches" and protocol §6. These say that a launch that returns without an error has an outcome even if no program ran, that a valid launch runs its whole grid whenever it returns without an error, and that `init` is the memory when the launch starts. Under stream capture (`torch.cuda.graph`, or Triton's own `triton.testing.do_bench_cudagraph`, which tutorial 11's benchmark uses), `k[grid](…)` returns without an error (compiling first if needed) and runs no program. The programs run at each `graph.replay()`, with the captured arguments, on the memory at the replay. work/graph_capture.py on the H200 shows this. The output kept its sentinel `-7` after the captured call, held `x + 1 = 2` after replay 1, and held `11` after the host set `x = 10` and replayed. A captured `n = 16` wrote 16 elements whatever the host's `n` was later. Capture with no warm-up compiled the kernel and ran nothing. If the captured call is the launch, its outcome is `ok` with memory unchanged, and `Compiler.Faithful` makes that a model outcome, which is false for any kernel that writes. If each replay is the launch, nothing says so, nor that its instance is the captured one and its `init` the memory at the replay, nor that it is in scope (a replay is not a call through Triton). Nothing excludes capture. A reviewer applying the claim to a host that captures, changes its inputs and replays would conclude the wrong outputs. Fix: in `Compiler.Faithful`'s "Which launch" (its docstring and its page), `TVA.Claim`, SEMANTICS "One launch" and `Launch.Valid`'s docstring, state that a call made while its stream is capturing is not a launch: it records the kernel and its arguments, allocates any descriptor scratch once, and runs nothing. State that each replay is a launch of the recorded instance from the memory at the replay's start, within the scope: nothing else writes its bytes, or the reused scratch, until it ends. Back this with TVA's evidence. Or exclude capture (exclusions.md and the scope), and say that a claim covers no captured call and no replay.
- **NEW** gap — The gate's reader of the citable facts (`stated_facts`, `tools/tvr.py`) is wider than the protocol says. It reads every table row from num.md's heading "Facts the library states" to the next `#` or `##` heading, so a `###` subsection with a table inside that section adds its first column to the list, whatever its heading says. In work/rule_probes.py Part C, a scratch num.md with a table under `### Shapes the facts use (not citable)`, holding `MathAcc` and `DivRn P .binary32`, gave 33 facts, and a field `MathAcc P .exp .binary32 …` passed `kinds`. The tree's page has one table, so nothing wrong is citable today. Protocol §5 says "by a code span in the first column of its table", and a library reviewer reading such a page could not see that the gate also reads the second table. Fix (cheap): read only the section's first table (stop at its first line that is not a table row, or at any heading), say so in §5, and have `fact_page_problems` name a section that holds more than one table.
- **NEW** wording — The L79 guidance gives, as module-level values to class and map, forms that round 15's supported subset excludes. REVIEWER_GUIDE §1 ("The code outside every function") gives "a `tl.constexpr(…)` global, a dtype (`OUT_T = tl.float16`), a namedtuple … Check that every module-level value the launch reads lies in the kernel lines and is mapped there". PROVER_GUIDE §1 says that a line binding "a `tl.constexpr(…)` global, a dtype" goes in the kernel lines, "where it is mapped (modelled, or dropped …)". Step 1 of the kernel reviewer's prompt and the kernel prover's prompt ("a module-level `tl.constexpr` or import included") say the same. SEMANTICS "The supported subset" (L88), merged beside it, admits at module level only Triton's modules as the source imports them and the module's `@triton.jit` functions, and lists "a `tl.constexpr(…)`, a dtype, a number" as excluded; REVIEWER_GUIDE §1's own subset paragraph calls such a kernel `UNSUPPORTED`. Fix: in these four places, say that the module-level values a launch may read are the imports of `triton` and `triton.language as tl` and the module's JIT functions, and that a kernel reading any other (a `tl.constexpr(…)` global, a dtype) is `UNSUPPORTED` (L88). Protocol §7's account of what the front end resolves can stay.
- **NEW** wording — The guides' lists of the host conditions in `Compiler.Faithful`'s scope leave some out, though each list points to the rule page. REVIEWER_GUIDE §1 ("The host code must stay within … scope") leaves out scope 5 (when the kernel builds descriptors, an allocator whose buffer holds none of the launch's bytes) and scope 6's condition that a `CompiledKernel` gets arguments of its specialisation (dtypes, alignment, integer class, a host descriptor's block shape). It also leaves out that an autotuned launch's `init` and arguments are those after the last hook. PROVER_GUIDE §2 ("The host stays within …") also leaves out `@triton.heuristics`, the `ASTSource` of `triton.compile`, the H200 target and `round_f32_to_tf32`. compiler-faithful.md's "How a bundle cites it" lists all of them. Fix: give the full list in both guides, or say "among them" and point to the page's checklist.
- **NEW** wording — evidence/tool-round16/out.txt (Part C, line 139) names a `docs/DESIGN` citation in REVIEW_PROTOCOL.md, while the README's table says "the tree cites no missing file". The protocol was fixed after the run, and on the merged tree the check finds no missing citation (work/rerun-tool-round16.out). Fix: re-run the evidence so that its output matches its README.
