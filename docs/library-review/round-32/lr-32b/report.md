# Library review, round 32, by lr-32b

## Verdicts

- **L141** ACCEPT — `semantic.dot` (`primitives/triton-3.8.0-semantic.py:1429-1520`) takes `out_dtype` from the accumulator, checks it equals the accumulator's dtype, and gives an int8 dot an `int32` result whatever `out_dtype` says; with signless IR integers a `uint32` accumulator has the result's type and is accepted, every other width is rejected by the verifier. SEMANTICS.md ("The only integer `tl.dot`"), rules/num.md and TRANSCRIPTION.md now say exactly this, with the `tl.bitcast .u32 .i32` model and `DotI8`'s room on the `int32` reading. evidence/num-dot-int8-round32 A1–A3 (ten accumulator dtypes by three `out_dtype`s, both paths, the room's edge, `c < 0` in the kernel) settles it.
- **L144** ACCEPT — `Rules.Compiler.Faithful`'s docstring, `Claim.Behaviour`, `Launch.Valid` and docs/rules/compiler-faithful.md now speak of one execution of the kernel's grid, and no framework page (docs/*.md, docs/rules, lean/TVA) names CUDA graphs (grep). A call that runs no program has no outcome, and a run of the programs is an execution like any other, so the rule stays true; the constants whose docstrings changed are listed.
- **L146** ACCEPT — scope 5 now excludes a launch on which the front end visits `tl.make_tensor_descriptor`, which matches the user's decision and removes the only source of a launch's global scratch (`TMALowering.cpp:166-184`). The claims whose sources contain the call (`scaled_mm_int8`, `fused_moe_bf16`) take `USE_TD = False`, so the call is not visited; `attn_fwd_f16`'s narrowing is listed.
- **L147** ACCEPT — "to a float of fewer bits" is Triton's test (`semantic.py:824-832`). Re-running evidence/front-end-round32 R1 gives the same output: both rounding modes are rejected for `bfloat16 ↔ float16` and accepted for `float32 → float16` and `float32 → bfloat16`.
- **L148** ACCEPT — the "`.type`" entry now says that a block's `.type` is not a dtype, and gives the forms the host rejects and the meaning of `x.to(y.type)`. Re-running Y1 gives the same output (nine forms).
- **L149** REOPEN — `SumDepth` itself is true. The lowering (`ReduceOpToLLVM.cpp`: `treeReduce` over a power-of-two count, the packed pair combined once more, one lane-bit butterfly per stage, at most two shared-memory rounds of the same butterfly) makes a perfect tree whatever the layout. My 310 extra reductions in `work/sum_depth.py` were all exact: linear layouts from `tl.reshape`, `tl.permute`, `tl.join` and `tl.interleave`; 3-D tiles along every axis; `tl.trans` of `wgmma` results with `N = 256`; a `float16` sum of a dot operand; 1-D axes of 32768 to 131072; 32 warps. In 976 rows of `tl.sum(x * y, axis=1)` with one element of the axis per thread, every thread's copy of a row's result was the same. The defect is in the exclusion this fix added. docs/exclusions.md, SEMANTICS.md ("Float `+` and `-`") and rules/num.md describe the excluded loop by its source ("a tile … produced directly by `tl.load`"), but the pass reads the IR after folding. `work/otl_noop.py` shows the loop rewritten (`2.0` stored where every association of the source gives `1.0`) when the source reduces `tl.load(p).to(tl.float32)` of a `float32` buffer, `x * SCALE` with `SCALE: tl.constexpr = 1.0`, `x / 1.0` or `x - 0.0`. A kernel reviewer who reads those operands as "not a load" then applies `SumDepth` and "no reassociation" to a rewritten loop. The text also calls the rewrite a reassociation, but the pass clones the update for the per-thread partial values: `acc = acc - tl.sum(x, 1)` stored `2.0` where the source gives `-1.0`, and `acc = tl.maximum(acc, tl.sum(x, 1))` stored `11.0` where it gives `4.0` (`work/sum_depth.py` L). The fix: state the pattern after constants are folded, naming at least a same-dtype `.to`, `* 1.0`, `/ 1.0` and `- 0.0` of a load (or exclude any such loop whose reduced operand is a load up to operations that fold away), and say that for an update other than the combine the result is not any association of the source.
- **L150** REOPEN — `DotF16Chunk` and `DotBF16Chunk` are false on `mma.sync` when an operand of the 16-bit `tl.dot` was converted in registers from an 8-bit dtype (`a = tl.load(fp8 or int8).to(tl.float16)`, as in a weight-dequantising matmul). The TTGIR then has `kWidth = 4`, and each instruction adds `k ≡ 0, 1 (mod 4)` of a 32-k block, then `k ≡ 2, 3`, not 16 consecutive k. `work/dot_partition.py` found this partition with zeroed probes, for fp8e5 and int8 sources, `K = 64` and `128`, 1 and 2 warps. `wgmma` and unconverted operands give 16 consecutive k. In `work/dot_counter.py` part 1, the per-instruction model with the observed partition equals the device on every element of the 96-element samples, for `float16` and `bfloat16`, with `a`, `b` or both converted, while the 16-consecutive model differs on about half. Part 2 is a counterexample: `K = 32`, accumulator `(1−2^-24)·2^-25`, products `1` at k = 0, `−1` at k = 2, `3·2^-25` at k = 1, and `(1−2^-11)·2^-25` elsewhere, with `a` from `float8e5`. The device gives `0`. Step 0 of the fact needs `s1 ≥ −15.006·2^-25`, step 1 needs `s1 ≈ −15.992·2^-25`, so no partial values exist (checked in exact rationals at every kink of the piecewise-linear slack). The derivation, the docstrings, rules/num.md ("one instruction per chunk of 16 consecutive k, both paths") and evidence/num-dot-chunk16 assume a partition this path does not have. The evidence's "converted" case was `float32 → float16`, which has `kWidth = 2`. Fix: state the facts per chunk of 32 consecutive k (two instructions, with constants re-derived for both partitions; the fp8 facts already use 32-chunks and are unaffected), or add the condition and an evidence part with converted 8-bit operands.
- **L151** ACCEPT — `semantic.sub` builds `p - i` as `add(p, minus(i))`, with `minus` the `0 − x` of `x`'s type (`semantic.py:261-267, 478-485`). The three `HSub` instances and `Ptr.sub_int` state that, and the SEMANTICS.md text covers the edge cases (the `int32` minimum, unsigned `k`, Python numbers, the rejected forms). Re-running S1–S3 gives the same output, and `Ptr.sub_int_of_signed` uses the standard axioms only.
- **L152** ACCEPT — the 23 predicates are compile-time tests of the dtype's name (`core.py:449-524`). The store into fp8 is stated as the saturating rounding to nearest even. Re-running T1 (299 kernels) and T2 gives the same output.
- **L153** ACCEPT — the exclusions row now says that tutorial 10's `mxfp8` and `mixed` formats run (`e4m3` by `e4m3`; and `e4m3` by `e2m1`, source line 230, so `DotScaledE4m3E2m1` in that operand order), and that `mxfp4` and `nvfp4` are rejected on the host at the tutorial's config. Re-running at `1024³` (`work/tut10_rerun.py`) gives the same shared-memory figures and the same largest error, `0.0625`.
- **L154** REOPEN — the parts done are right. (1) `tl.itofRel_binary32` holds: the second alternative is exact below `2^53`, the third is only for 16-bit formats, and it uses the standard axioms only. (3) `DivF32InfDivisor` rests on an exhaustive measurement (every finite `float32` by `±∞`, through `div.full.f32` with a runtime divisor). (4) The descriptor strides have their evidence. Two of the four items are left undone with nothing to track them: (2), narrowing `AddRel` to a product operand, and the `tl.exp` overflow fact (`+∞` from `0x42b17218`, measured in evidence/num-special-f32 E1 but not stated). Fix: state them, or split them into a new issue so that this one closes.
