## New issues

- **NEW** wording — SEMANTICS.md "Programs" (line 153) says that "a tensor step that uses any lane of an atomic's result depends on every lane". The "Atomics" item (lines 795-797) says that such a step "holds it back, as a whole", and review-questions.md Q7 (line 235) says the same. `Step.defer` is finer than that. A step may pass a pending lane whose old value changes neither its memory nor its event. For example, `tl.store(OUT + x, r, mask=x == 0)` waits only for lane 0, because `writeAll` skips the disabled lanes and `accBytes` reads only the addresses. What is coarser than the device is that one tensor step waits for every lane it uses, and every later step of the program waits for that step. Fix: use the wording of "Granularity" and Q17 in all three places: a tensor step that uses one lane's result holds back every later atomic of the program.
- **NEW** wording — Two evidence READMEs still describe, in the present tense, release-check steps that were removed in round 35 (library issue L160). Conclusion 5 of `evidence/gate-round7/README.md` says "The release check also compares each recomputed gate with the shipped one". Question 5 and conclusion 5 of `evidence/tool-round18/README.md` describe the `pages` step. Fix: add the "Since round 35" note that `evidence/release-check/README.md` carries.
- **NEW** wording — The `gate` row of `docs/LIBRARY_REVIEW.md` (line 106) asks whether `tvr release` can pass a library that fails the build, `tvr library-check`, the records, the lint or the audit. It omits the release check's own purpose, which is the `shipped`, `packages` and `sandbox` steps: a library that depends on anything it does not ship. It also says that the audit reads only "the text" of `kernels/` and `claims/`, but `kernel_independence` also checks the Lean imports of kernels. Fix: add "or depends on anything it does not ship" and "the text and the imports".
