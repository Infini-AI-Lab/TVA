# Library review, round 8, by lr-8a

## Verdicts

- **L1** ACCEPT — The "Which value" reading is what 3.8.0 does: `set_attr` (`ir.cc:411-425`) marks the operation that defined the value, and for a block argument it sets only an `…_arg<N>` attribute on the loop (nothing for a function's parameters). `_find_carries` (`code-generator.py:465-503`) visits the body once with the names bound to their values before the loop, then erases that block. All 13 cases of evidence/hint-loops reproduce exactly: C2, C9, C11 and C13 fault, and false hints on parameters and induction variables (C5–C7) have no effect. The constants list is right (docstrings only).
- **L2** ACCEPT — The readings are sound. A hint replaces only the hinted vector (`AxisInfo.cpp:1244-1259`), and the `AxisInfo` constructor applies the divisibility of a dimension with contiguity 1 to every element (`AxisInfo.h:92-101`). So `ContigIs` for `max_contiguous` alone, and "every element" for `multiple_of` alone, are the only readings checkable from the values that cover what the compiler then believes. evidence/hint-rank2 reproduces in all 15 cases, and `work/hint_weaker.py` W8 (C1 again) faults. On the coordinator's question: tutorial 08's `tl.multiple_of(a_ptrs, [16, 16])` is also false under Triton 3.8.0's own documentation. `core.py:3308-3318` says that along a dimension of contiguity 1 every element must be a multiple of `values[d]`, and dimension 0 of `a_ptrs` has contiguity 1. The compiler believes the same thing, so no reading that is sound against that belief makes the hint true. Tutorial 08 runs correctly with aligned rows only because its loads use dimension 1. Tutorial 09 can be claimed on full tiles only: on a partial tile the compiled loads read other elements (T2). Two readings are stronger than Triton relies on (NEW gap below), but changing them would help neither tutorial. The list of changed constants is complete: no other library constant and no kernel uses the hint definitions.
- **L5** REOPEN — The scratch part holds: evidence/desc-scratch reproduces, and D4 again overwrites 1024 elements. But the new `tl.make_tensor_descriptor` admits a zero shape entry (`0 ≤ x.toInt`), and `TensorDesc.Valid` sets no lower bound. On the H200, every load or store through an in-kernel descriptor that has a zero dimension faults with "an illegal instruction was encountered" (`work/desc_edges.py` E2, E3, E5), while the model gives the padding or writes nothing. So `Compiler.Faithful`'s "never faults" is false for that well-behaved model. Building such a descriptor without accessing it is harmless (E7). A host-built descriptor with a zero dimension is rejected on the host (`AssertionError: shape must be positive`, E6). A zero leading stride and a stride of `2^40` elements behave as the model says (E4, E8). Fix: make an access through a descriptor with a shape entry `0` undefined behaviour (`0 < shape` in `TensorDesc.Valid`, or in `make_tensor_descriptor`'s condition), say so in SEMANTICS "Tensor descriptors", and add these cases to the evidence.
- **L21** ACCEPT — It matches `autotuner.py:133-282`. Each timing run is the config's `pre_hook`, the autotuner's `pre_hook`, the run and its `post_hook`. After timing, the autotuner calls `pre_hook(reset_only=True)`, then the chosen config's `pre_hook` on every call, then makes one launch. I re-ran evidence/autotune-launch: the counts vary from run to run (3876 against 3884 runs on `x`), and the order of the last three hooks is the same.
- **L28** ACCEPT — evidence/runtime-if reproduces exactly. The facts match `visit_If`, `visit_IfExp` and `visit_BoolOp`, and the cast to `int1` (`cmpi ne`, `cmpf une`). One sentence is too broad (NEW wording below).
- **L29** ACCEPT — evidence/scalar-args reproduces; only a tensor address differs. The facts match `specialize.cc`: `handle_long_type` makes `1` a constexpr, picks `i32`/`i64`/`u64` by range and marks multiples of 16 `D`; `handle_bool_type` gives `u1`; `handle_float_type` gives `fp32`. Annotated types wrap, truncate or reject as stated.
- **L30** ACCEPT — `_block_ptr` (`core.py:1828-1936`) defines only `advance`, `load`, `store` and `_materialize`, and no operator. `load` and `store` build `int64` coordinates, pointers and masks and call the plain `load`/`store`, as `TVA.Lang.BlockPtr` says; without `padding_option`, `other` is `None`. The aggregate exclusion is narrowed consistently.
- **L37** ACCEPT — exclusions.md records the user's decisions with their citations: tutorial 05's `_layer_norm_bwd_dx_fused`, tutorial 11, and targets other than the H200. Tutorial 06's hint on an induction variable has no effect (L1, C5). Tutorial 08 remains without any claim, which is for the user to decide (NEW gap below).
- **L44** ACCEPT — The list follows the user's decision. The options left out of it change results (`enable_fp_fusion`, `input_precision`, `max_num_imprecise_acc`) or the order of a program's accesses (`num_stages`, `warp_specialize`). `volatile` and the cache modifiers change only how concurrent accesses are seen, and a well-behaved model has none to the same bytes.
- **L45** ACCEPT — All of evidence/promotion reproduces. `table.py` gives the same 40240 lines and `rules.py` finds 0 differences. `lean_compare.py` compares 37896 cases and finds 0 differences. `device.py` and `constants.py` give identical output. Spot checks against the source: `computation_type_impl`, `to_tensor_type`, `cast` (`int1` as `!= 0`, `fp16`/`bf16` through `fp32`), `truediv` (two integers to `float32`), `mod`, and the tensor's comparison methods, which call `to_tensor` first (`core.py:1048-1090`). The fix to the comparison constant is right (K1–K4), and no Lean definition changed. But PROVER_GUIDE still states the old rule (NEW soundness below).
- **L47** ACCEPT — evidence/compiled-launch reproduces exactly. Scope point 6's classes are those of `specialize.cc`. Asking for the same class (rather than "no stronger") is more than needed, but sound.
- **L49** ACCEPT — evidence/other-writers reproduces: 20 of 20 trials stay correct with writers to the neighbouring bytes, in the same 4-byte words, against 0 of 20 in the control; the timings vary. `TVA.Rules.Compiler`, `TVA.Claim`, `Launch.pdl`, SEMANTICS and exclusions.md say the same thing. The claimed kernel of that evidence rewrites its own data, which no claim covers, but it still shows what it is for: the other writer's stores never reach the claimed bytes.

## New issues

- **NEW** soundness — `docs/PROVER_GUIDE.md` ("Write each Python number as the constant Triton builds") still gives the rule that L45 corrected. It says a number "with an operator or `tl.where` … in the operation's dtype", and an operator includes a comparison. SEMANTICS "Constants" and evidence/promotion K1 and K3 say that a comparison first makes the number a tensor of its own type: `x < 0.1` on `float64` compares with `float32(0.1)` widened, and is true for `x = 0.1`; `x < 2**31` on `int32` compares in `uint32`. A prover who follows the guide writes a model that differs from the device. Fix: "with an arithmetic or bitwise operator, or as a value of `tl.where`", as SEMANTICS says.
- **NEW** gap — Two hint readings are stronger than what Triton 3.8.0 documents and relies on, so correct launches have no claim.
  - `multiple_of` alone on `base + tl.arange(0, B)` is false on every launch under the "every element" reading, yet it is the common 1-D idiom, and evidence/hint-loops' "promise true for" column calls the cases that use it (C1, C3, C8, C10, C12) true. 3.8.0 pairs `v` with the contiguity it infers for an arange, `B`, and the result is correct (`work/hint_weaker.py` W1).
  - With a `multiple_of` on the same value, `max_contiguous` needs only `ContigAlong`, because the hint replaces the inferred divisibility (`AxisInfo.cpp:1244-1259`). W3, W4, W5 and W7 are correct with a `C` below the value's own contiguity, which `ContigIs` makes undefined. W8 shows that `ContigIs` is needed only when `max_contiguous` is used alone.

  Fix: state the combined reading `ContigAlong ∧ FirstsDiv`. Also state, as a library fact, the contiguity the analysis gives the shapes kernels use (`tl.arange`, plus a scalar or a value constant along the axis): `FirstsDiv x k C v` with any such lower bound `C` covers the compiler's belief. Then correct the column in evidence/hint-loops.
- **NEW** gap — Tutorial 08's `grouped_matmul_kernel` has no claim on any launch. Its `[16, 16]` hint is false under Triton's documentation and under the compiler's belief (L2 above), so L37's target needs a user decision: exclude the kernel or its two hint lines, or add a library fact on how 3.8.0 uses the slow dimension's divisibility of a pointer block that only `tl.load` and `+ scalar` use. Such a fact needs a reading of every `AxisInfo` consumer in 3.8.0, which is beyond `primitives/`. Tutorial 09 is coverable on full tiles only (`M` and `N` multiples of the blocks). Its partial tiles would need a lowering fact: which elements the vector loads read for the lanes past `N`.
- **NEW** wording — Four texts say more than is true.
  - SEMANTICS "Index arithmetic": "arithmetic on them stays `int32` … until the source casts it" is false when an operand is a runtime `int64` or `uint64` scalar, which promotion widens to. Say "unless promotion widens it ('Operators and promotion')".
  - SEMANTICS "A runtime `if`": "otherwise the kernel is rejected" is too broad. A name defined in one branch only is rejected only when it is used after the `if` (`work/if_names.py`).
  - Builtin `min`/`max` of compile-time values reject NaN and `-0.0` (`core.py:3884-3886`).
  - PROVER_GUIDE still calls L1 and L2 open and tells provers to write every hint, but a hint on a parameter or an induction variable is now dropped.
