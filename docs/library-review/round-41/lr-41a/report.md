## Verdicts

- **L184** ACCEPT — The twelve enabled-lane lemmas of `Tile2` now take row and column lane values `ρ i`, `κ j` of any form, and their bound is `ρ i < M` and `κ j < N`. A caller's `r0 + i` hypothesis still fits, since Lean takes `ρ = fun i => r0 + i`. The new `MaskAt`, `ElemAt` and `Buf.tileAt` have the old `MaskOk`, `Elem` and `tile2` as instances: `maskOk_iff_maskAt` is `Iff.rfl`, and `elem_iff_elemAt` and `tile2_eq_tileAt` are proved. The load rule `safe_load_tileAt` needs no injectivity, which is right, because `% M` rows may repeat. The store rule `safe_store_tileAt` needs distinct enabled rows and columns (`hρ`, `hκ`), and `add_inj` gives both for `r0 + i`. `irem_ok`, `irem_toInt` and `safe_irem_lanes` give lane `i` of `tl.irem x M` the value `f i % M` when `x`'s lanes are the naturals `f i`. Since both operands are non-negative, this agrees with Triton's signed remainder. With `maskAt_cols` (`Nat.mod_lt`) it covers tutorial 03's `a` tile, which has no row mask. The author's probe runs that tile from the `int32` lanes to `safe_load_tileAt`. I re-ran the probe and got the same output. No device fact is involved, and the changed constants are listed.

Between integer dtypes other than `int1`, that conversion has one result, `castInt`, so either form transcribes `x.to(d')`. `IntV.cast_eq_ofInt`, the 64 lemmas `ConvRel.iff_cast_<d>_<d'>` and `safe_convert_iff` prove this, and the probe uses them in both directions. No definition changed. Triton 3.8.0's `cast` (`semantic.py:870-880`) sign-extends exactly when the source is signed and not `bool`, which is `IntV.cast`. On the device, `work/int_cast_gpu.py` ran all 64 pairs of `int8`…`uint64` on boundary values. Out of 920 values, `x.to(d')` was 0 times different from `IntV.cast` (the value modulo `2^w'`). The new TRANSCRIPTION.md row rests on these stated facts.

## New issues

- **NEW** soundness — The gate can pass a kernel whose own Lean is never compiled. `kernel_lakefile` (`tools/tvr.py`) declares one `lean_lib` per kernel folder with `roots = [<module's first component>]`. Neither it, `manifest_problems` nor `check` refuses two kernels whose modules have the same root. With two such libraries, `lake build <Module>` compiles only one file, from the library listed last, and both write the same `.lake/build/lib/lean/<Module>.olean`. The claim reader and `leanchecker` then read that build. In a scratch copy (`work/same_root.py`, output in `work/same_root.out`), I made `vec_add_aa`, a copy of `vec_add_f32` with the same module (`VecAdd`) and namespace. I appended `theorem Kernels.VecAdd.broken : (1 : Nat) = 2 := rfl` to its Lean file. `tvr check vec_add_aa` passes all 13 checks with `vec_add_f32`'s digest, even though `lake env lean` on its own file fails. Copying a kernel folder to start a new one leads to exactly this case, and the claim the gate then reports is another kernel's. This flaw is older than L187; the old shipped lakefile had the same gap. Fix: in `manifest_problems` (or `check`), refuse a module whose root is another local kernel's root, or a root of Lean or a package the manifest pins (`Init`, `Lean`, `Std`, `Lake`, `Batteries`, `Aesop`, …). Alternatively, build each kernel with a configuration that declares `TVA` and that kernel's library alone. Say which in REVIEW_PROTOCOL §2 ("Lake").
- **NEW** gap — Nothing checks that the fixed claims still elaborate. The user required on 2026-11-10 that library changes keep the 41 claims unaffected. L189's breakage was found by hand. `tvr release` builds `TVA` in a sandbox that ships `claims/`, but no step elaborates a `claims/*/Claim.lean`. A round like round 39 would therefore still pass the release check. Fix: add a release step after `build` that runs `lake env lean` on every `claims/*/Claim.lean` and fails on any error. All 41 take a few seconds each here. Then list the step in REVIEW_PROTOCOL §2 and in LIBRARY_REVIEW's `gate` row.
- **NEW** wording — Two shipped guidance pages still treat `kernels/` as shipped, and L188's sweep missed them. `docs/PROVER_GUIDE.md:34` and `docs/DESIGN.md:124` give `kernels/vec_add_f32/lean/VecAdd.lean` as the worked example of a whole claim, which a prover outside the working tree does not have. `docs/DESIGN.md:60`'s layout lists `../kernels/` with no note that it is local. The citation check does not see these, because they are code spans. Fix: point the example at a file that ships, or say it is local only. Mark `kernels/` as local in DESIGN.md's layout.
