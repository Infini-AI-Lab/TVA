## Verdicts

- **L144** ACCEPT — "or never" is gone. `TVA.Claim` (module docstring and `Behaviour`), `Rules.Compiler.Faithful`, docs/rules/compiler-faithful.md, SEMANTICS.md ("One launch", "Launches") and REVIEW_PROTOCOL.md §6 now say that a host call that only records the grid, for a run a later call makes, is not an execution, and that the launcher's skip of `2^31` to `2^32` programs is not such a call: it ends `ok`, and `Launch.Valid` (`L.grid 0 < 2^31`) keeps it out. This agrees with "a launch that returns without an error has an outcome", so the L9 vacuity is gone. A grep of docs/*.md, docs/rules and lean/TVA finds no mention of CUDA graphs and no "or never".
- **L146** ACCEPT — scope 10(c) (`lean/TVA/Rules/Compiler.lean:217`, docs/rules/compiler-faithful.md:287) and the exclusions.md row now both list `triton.set_allocator`, with the same reason (no global scratch within scope 5, `nvidia-driver.py:301-321`). Re-running evidence/set-allocator gave identical output: seven in-scope kernels, scratch `0`, and the allocator called `0` times; the control called it once.
- **L149** REOPEN — the restated pattern covers every form in round 32's probes (lr-32a's U1–U7 and F1–F8, lr-32b's `otl_noop.py`), and the "folds to a load" test can be checked on the operand ("gives back every element unchanged, whether or not Triton folds it"). But the rest of the pattern is still worded on the source, and `work/otl_wording33.py` (H200, exact values, `2.0` stored where the source gives `1.0`) shows rewritten loops that the wording sends to "not rewritten": (a) an identity between the reduction and `U`, or after `U`: `acc + tl.sum(x,1).to(tl.float32)`, `acc + tl.sum(x,1) * 1.0`, `(acc + tl.sum(x,1)) * 1.0`, `acc + -(-tl.sum(x,1))`; (b) a second use that is dead: `dead = s * 3.0` unused, `acc * 2.0` unused, a store under a constexpr-false `if`, all against "a reduction whose result has another use"; (c) the reduction under a compile-time `if` ("not inside an `if` of the body"), or in a `tl.static_range(1)` nested in the `for`; (d) a reduction or update in a helper (the text names helpers only for the load); (e) an initial value `tl.zeros(...) + iv` with `iv` a runtime int argument equal to `1`, which Triton specialises: it stored `3.0` for `2.0`, against "an initial value computed at runtime" (with `iv = 0`, not rewritten). Fix: state the whole pattern on the IR, that is after inlining helpers, resolving compile-time `if`s, unrolling `static_range`, specialising int arguments equal to 1 and dropping unused values, with identities allowed anywhere in the chain from the reduction to the next carried value. Or exclude more broadly: any `for` loop in which a float reduction of a load (up to identities) along the last axis of a tile of rank ≥ 2 reaches a loop-carried value. Add these forms to evidence/thread-locality. My static scan of the claims' sources (`work/otl_claims_scan.py`) finds no reduction of a load inside a runtime loop, so no claim is affected that I can see.
- **L150** ACCEPT — the facts are true as restated. (1) Re-running evidence/num-dot-chunk16-round33 gave identical output (Part P: 104 configurations; Part M: 2605056 element results equal to the model, no chunk outside the bound, worst ratio 0.381). (2) The source settles which `kWidth` can occur: `computeOrigBitWidth` (`AccelerateMatmul.cpp:385-427`) takes the narrowest load (at least 8 bits, since an `i1` pointer loads `i8`, `semantic.py:1036-1040`), halves it at most once for a `tl.join`, and returns 4 for `Fp4ToFp`, which only Gluon or `dot_scaled` create. So `kWidth ≤ 8`. (3) `work/dot_partition33.py` probed 506 more configurations on the device: both formats; `a` from fp8e5, fp8e4nv, int8, uint8 and bool, `tl.join`, join then permute, nested joins, a transposed int8 load, a masked load, `float16 → float32` join; `b` from fp8e5, transposed, int8 join-unpacked; host descriptors; fed-back K loops with `KT` of 96, 160 and 192 (not multiples of `BK`, last block masked); 1 to 8 warps on both `mma.sync` and `wgmma`. `kWidth` was 2, 4 or 8, and every instruction's `k` lay in one aligned block of 64, in increasing order (widest span 58). A bool host descriptor is rejected at compile time (TMA lowering). (4) I re-derived both arms: `17·(1+17+33+49) + 4·96 = 2084` (`·2^-25·Mj`), `2^-21·|s+c|`, `21·2^-149`; and `(1+15·2^-25)·A_j + 2^-23·Mj + 2^-21·|s+c| + 5·2^-149`. The constants keep a margin of about 2, and the Lean `def`s match the docstrings and rules/num.md. The changed constants are listed.
