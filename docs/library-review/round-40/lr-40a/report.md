## Verdicts

- **L180** ACCEPT — `addrs_tile2`, `accBytes_tile2`, `safe_load_tile2` and `safe_store_tile2` now take `hp` on the enabled lanes only (`r0 + i < M → c0 + j < N → …`). The twelve `…_on` lemmas give that form from the matrix bound `(M - 1) * s0 + (N - 1) * s1 < 2^(w-1)`, or from each term's bound for `base + x + y`, which is right because each term is added to the pointer on its own. The fact behind the change holds on the device. `work/masked_wrap.py` (Triton 3.8.0, H200 NVL, 2026-11-10) uses lr-39b's numbers (`M = 1000`, `BM = 64`, `s0 = 2149000`, `N = BN = 16`, `s1 = 1`). The `int32` offsets of rows 1000–1023 of the last tile wrap to negative values. The buffer lies `2^31` bytes into a larger allocation, so the wrapped addresses are our own mapped canaries rather than a fault. The masked load gives every enabled lane its element and every other lane `other`. The masked store writes exactly the enabled elements and leaves the canaries and every other byte unchanged. `work/llir_flags.out` shows the offset product as a plain `mul i32` (no `nsw`) and the `getelementptr`s without `inbounds`, so nothing in the compiled code assumes the wrap away. `Block`'s existing statements are unchanged (git diff). `fits_of_dvd`, `fits_of_pow2` and `fits_of_lt_pow2` are stated as their names say. The header correctly says why the 1-D block keeps the every-lane bound: its mask compares the offsets themselves. `work/Probes.lean` stores the last partial tile of an `int32` `pid * BM + tl.arange(0, BM)` transcription through `ptr_lane_seq_on`, `maskOk_and` and `safe_store_tile2`, with the matrix bound alone. It also shows that the last block of `n = 2^31 - 1` fits by `fits_of_lt_pow2`.

## New issues

- **NEW** gap — `TVA.Lemmas.Tile2` covers only rows (columns) whose lane `i` is `r0 + i`: `Tile2.Elem`, `MaskOk` and every lane lemma fix the row to `r0 + i`. The pattern of tutorial 03, `offs_am = (pid_m * BLOCK_SIZE_M + tl.arange(0, BLOCK_SIZE_M)) % M` (no row mask, every lane enabled, row `(r0 + i) % M`), is used by the test-set kernels `matmul_f16`, `matmul_e5m2` and `block_fp8_matmul`, by `fused_moe_bf16` (`% N` in `int64`) and by `lora_shrink_bf16` (`offset_n % N`). No library statement reaches it, so each of these kernels re-derives its tile footprint and load in its own Lean. Fix: generalise `Tile2` (`Elem`, `MaskOk`, the lane, footprint and load/store rules) to row and column lane values `ρ i`, `κ j`, of which `r0 + i` is one instance. Add a lane lemma for `tl.irem (r0 + tl.arange) M` (`ρ i = (r0 + i) % M < M`) from `IntV.toInt_of_rem?_nat`.
- **NEW** wording — The integer cast is described three ways that disagree. `Tensor.castInt` (`lean/TVA/Lang/Tensor.lean`, "Integer cast of each element (`x.to(tl.int64)` etc.)") and `IntV.cast` (`lean/TVA/Lang/Scalar.lean`, "`x.to(tl.intW)`") say that `castInt` is `.to(…)`. The round-40 docstring of `Tensor.get1_castInt` (`lean/TVA/Lemmas/IntW.lean`) says that it is not, and that `.to(…)` and the promotion are `tl.convert`. Three of TVA's fixed claims write `.to(tl.int64)` or the `int64` promotion of `tl.arange` as `castInt`: `claims/rotary_varlen_bf16` (line 98), `claims/recompute_wu_bf16` (lines 103, 253) and `claims/ssd_chunk_scan_bf16` (line 444). A reader can no longer tell whether those transcriptions are faithful. They are: for integer dtypes other than `int1`, `ConvRel`'s only result is `IntV.cast` of the operand. `ofIntRel` is the value modulo `2^w`, and `cast` sign- or zero-extends by the source and then truncates. `work/Probes.lean` proves `ConvRel P .i32 .i64 a (IntV.cast a)`. Fix: make the three docstrings say one thing, and state the bridge as a lemma, for example `ConvRel P d d' x r ↔ r = IntV.cast x` for integer `d`, `d'` other than `int1`, or `tl.convert d d' x = pure x.castInt`. A prover could then move between the two forms, and a reviewer could accept either transcription.
