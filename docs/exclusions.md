# Exclusions

These Triton features are hard to give meaning to, rarely used, or both. A model may not use
them; a kernel that needs one is out of scope until the library covers it.

| Feature | Why excluded | What a model does instead |
|---|---|---|
| `tl.debug_barrier` semantics | the language has no threads; user: "we do not need debug semantics here"; a barrier would only order accesses that already conflict within the program (below), or two atomics on the same bytes, whose every order the semantics already allows (`Step.defer`) outside the exclusion of an atomic's result used on a shared cell (below; library issues L161, L165): inside it the device gives orders the semantics lacks, and a barrier would remove some of them ([evidence/atomic-result-order](../evidence/atomic-result-order/README.md), `variants.py`), but it keeps no meaning there either, and such a launch stays excluded | treat the call as a no-op |
| a program that writes and reads back its own data, or updates an input in place: two global accesses of one program to the same bytes, at least one writing them (a store or an atomic), unless both are atomics on the same bytes, across loop iterations included | one program is not sequential for global memory: its threads access memory with no barrier, and Triton's pipelining reorders loop iterations ([evidence/intra-program](../evidence/intra-program/README.md)); user, 2026-10-27 (library issue L15): no conflicting accesses within a program | out of scope: such a model is not well behaved (`IntraRace`), and no claim covers it. A barrier-phase model may be added later |
| atomics of one program on partly overlapping bytes (different widths at overlapping addresses) | not two atomics on the same bytes | a conflict within the program, as above |
| `tl.device_print`, `tl.device_assert`, `tl.static_print` (and Python's `print` and `assert`) as debugging aids | no effect on global memory without `debug` | drop the call when what the front end evaluates in its arguments has no effect; otherwise those operations are model lines ([SEMANTICS.md](SEMANTICS.md), "How the front end evaluates the source") |
| `tl.inline_asm_elementwise` | arbitrary PTX | out of scope |
| `float8e4b15`, AMD fp8 formats (`float8e4b8`, `float8e5b16`) | not used on the target GPUs | out of scope |
| pointers to pointers (`tl.pointer_type` of pointers) | rare; needs a typed pointer memory | out of scope |
| `range` with a non-positive step | rare; not modelled yet (constant negative steps follow Python's semantics, `code_generator.py:1246-1251`) | `tl.forRange` is undefined behaviour there |
| `range` with unsigned bounds at or above `2^(w−1)` | `scf.for` compares signed | `tl.forRange` is undefined behaviour there (`tl.RangeOk`) |
| descriptor reductions (`desc.atomic_*`) into elements other programs also reduce into | TMA reductions are relaxed: they race in the semantics (an SC interleaving would hide their reorderings) | out of scope; covered when one program owns the elements ([review-questions.md](review-questions.md) Q10) |
| pointer and descriptor accesses to the same bytes | a program's accesses are not ordered anyway (library issue L15): such a pair with a write is already a conflict within the program, or a race between programs, except two atomics, a pointer atomic and a descriptor reduction (`desc.atomic_*`), which do not conflict but whose atomicity across the generic and the TMA (async) proxy is not confirmed; two reads need no order, and are kept out until [review-questions.md](review-questions.md) Q11 is settled | out of scope |
| 3-D (batched) `tl.dot_scaled` | only the 2-D form is in the library | ask for the operation in the library |
| `tl.histogram` with an enabled value outside `[0, bins)` | undocumented | undefined behaviour in `tl.histogram`: the prover shows values are in range |
| `desc.scatter` with an out-of-bounds lane | undocumented | undefined behaviour in `tl.desc_scatter` |
| programs that *wait* on each other (locks, spin loops, cooperative grid sync) | no progress rule yet | planned ([plan/PLAN.md](plan/PLAN.md)); accumulation through atomics is covered by `TVA.shared` |
| data passed between programs through plain memory behind a flag or counter ("the last program reduces the partial tiles", semaphore split-K, a lock) | a scalar atomic is issued by one thread with no barrier before it, so its release does not publish the other threads' writes; the semantics has no synchronises-with, so such launches race | out of scope |
| a counter that hands out work (`tile = atomic_add(cnt, 1)`) | `TVA.shared` needs footprints fixed in advance | out of scope until footprints may depend on the values the atomics return |
| `num_ctas > 1` | a program is a cluster of CTAs; `cta`-scope atomics are atomic only within one CTA | `Launch.Valid` requires `num_ctas = 1` |
| the 64-bit Philox (`uint64` offsets as counters) and `tl.randn` | not modelled | `tl.randint`/`tl.rand` cover the 32-bit generator |
| `cta`-scope atomics used across programs | atomicity only within a CTA | they race; the launch is not well behaved |
| lanes that hold LLVM poison (`x.to(int)` out of range, a shift by the width or more) but whose values are never used | poison is read conservatively as undefined behaviour | the model is undefined there; a kernel that converts unspecified masked-off lanes needs `other` or a `tl.where` before the conversion |
| relaxed / acquire-only / release-only atomics on memory other programs touch, when the program uses the value they return | an SC interleaving would hide their reorderings | they race unless ordered, and, used on a cell another program or another atomic operation of the program also accesses, they are excluded whatever their order (next row). Those whose returned value the source never uses, at `gpu` or `sys` scope, are covered: their model is the `acq_rel` atomic (`MemSem.unused`, `tl.atomic_add_unused` and the others; [SEMANTICS.md](SEMANTICS.md), "Atomics"; [evidence/relaxed-atomics](../evidence/relaxed-atomics/README.md); library issue L157, user decision 2026-11-08) |
| a program that uses the result of a `tl.atomic_*` call (`add`, `xchg`, `cas`, `max`, `min`, `and`, `or`, `xor`; in a store, an address, a mask, a branch or any other operation that runs, of any lane, with any `sem`) when a cell that call reaches is also accessed by another program of the launch, or by another atomic operation of the same program (another `tl.atomic_*` call, or the same call run again in a loop; the lanes of one call are not another operation) | the semantics orders a program's steps: a tensor step that uses one lane of an atomic's result holds back every later atomic of the program (`Step.defer`), while on the device each thread orders only its own accesses; library review lr-34a found a well-behaved two-program launch (with `acq_rel`; with `relaxed` it races, library issue L165) whose device outcome the semantics lacks, and a one-program launch of two calls on one cell shows the same, with `acq_rel` and with `relaxed` ([evidence/atomic-result-order](../evidence/atomic-result-order/README.md), 200 of 200 runs each); user, 2026-11-08 (library issue L161): "let's exclude with Fix B" | out of scope, checked on the source as an unused result is, and a cell the reviewer cannot tell is unshared counts as shared (library issue L165) ([SEMANTICS.md](SEMANTICS.md), "Atomics"; `TVA.UsesSharedAtomicResult` reads the first case on a model, and `TVA.AtomicResult.crosswarp_excluded` shows lr-34a's launch under it); work queues, tickets and locks wait for a per-lane model ([review-questions.md](review-questions.md) Q17). No claim uses an atomic's result |
| `tl.atomic_and`, `tl.atomic_or`, `tl.atomic_xor` on `float32` or `float64` elements | rare; Triton 3.8.0 accepts them and performs the integer operation on the bit patterns (`and.b32`, …, `xor.b64`; [evidence/atomic-dtypes](../evidence/atomic-dtypes/README.md), library issue L168), but the library gives them no meaning | out of scope: `bitUpd` has no new value for a float, so the model's atomic is undefined behaviour ([SEMANTICS.md](SEMANTICS.md), "Atomics"). Element types Triton rejects on the host (`bool`, 8-bit, `float8`; 16-bit except in `atomic_add` of `float16`/`bfloat16` and `atomic_cas`) need no exclusion: such a launch has no outcome |
| `debug=True` (`TRITON_DEBUG`, the knob, the launch's or a config's `debug`, the decorator's, or the kernel's `JITFunction` attribute set from Python, `kernel.debug = True`) | asserts and overflow checks trap (with the attribute set, an `int32` overflow trapped: [evidence/host-round20](../evidence/host-round20/README.md) D1; library issue L105) | `Compiler.Faithful` covers `debug = false` only (`Launch.debug`); a `kernel.debug` set by code other than the kernel's source, and `TRITON_DEBUG` or the knob, are assumed not to happen, part (B) of the scope, which nobody checks (the user's decision, 2026-10-29: "So basically, we want to verify the kernel itself, rather than triton installation or other code programmed by users.") |
| aggregate classes a kernel or a library other than Triton's language defines (classes made with Triton's `_aggregate`, `triton.language.core`) | their operators, subscripts and methods are `@triton.jit` functions Triton inlines, so an operator on them may run any operation; the library gives them no meaning | out of scope; an operator on an aggregate may run any operation ([SEMANTICS.md](SEMANTICS.md), "How the front end evaluates the source"). Triton's own block pointer (`tl.make_block_ptr`, `_block_ptr`) is covered through its operations (library issue L30) |
| programmatic dependent launch (`launch_pdl=True`) | the kernel may start before the previous kernel on the stream has finished writing, so its programs may read memory other than the claim's `init` | `Launch.Valid` requires `pdl = false`; `gdc_wait` is then a no-op ([SEMANTICS.md](SEMANTICS.md), "Launches") |
| a kernel that calls `gdc_launch_dependents()` followed on its stream by a launch with `launch_pdl=True` that writes a byte the kernel is given | that launch may start while the kernel still runs, and write memory the kernel reads ([evidence/pdl](../evidence/pdl/README.md) part D) | assumed not to happen, part (B) of the scope, which nobody checks (the user's decision, 2026-10-29: "So basically, we want to verify the kernel itself, rather than triton installation or other code programmed by users."): `Compiler.Faithful` covers a launch whose bytes nothing else writes until it ends; without such a next launch, `gdc_launch_dependents` is a no-op ([SEMANTICS.md](SEMANTICS.md), "Launches") |
| anything else that writes a byte the launch is given (its `init`, the buffers of `Pre`) from the launch's start to its end: the host, a kernel on another stream or device | the claim is about the launch's own outcome from its `init` | assumed not to happen, part (B) of the scope, which nobody checks (the user's decision, 2026-10-29: "So basically, we want to verify the kernel itself, rather than triton installation or other code programmed by users."): `Compiler.Faithful` covers a launch whose bytes nothing else writes until it ends; writes to other bytes, concurrent or not, are allowed ([rules/compiler-faithful.md](rules/compiler-faithful.md), "Scope" 1; library issue L49) |
