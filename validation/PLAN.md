# Differential testing of TVA v3

Draft for review with zhuominc (Yi Zhou, 2026-11-11). Nothing here is part of the library.

## Goal

Every one of the 41 claims has a proof (`claims/<kernel>/oracle/`), so inside the model there is
nothing left to check: every covered launch of each model is correct. What a reader of a proved
claim still trusts is listed in `TVA/Claim.lean`:

1. Lean and Mathlib;
2. **the transcription**: the model is the kernel;
3. **the compiler**: Triton compiles a direct launch so that every execution ends in one of the
   model's outcomes, with the meaning `TVA.Triton` gives each `tl.*` operation;
4. **the device facts** (`Device P`, 38 fields), measured in `evidence/`.

Items 2–4 are claims about the real GPU, so they can be tested against it. The question every
test asks is one direction of refinement:

> Is what the device did one of the outcomes the model allows?

A device behaviour outside the model's outcomes is a **soundness finding**: a proof covers a
program the device does not run. The other direction (the model allows more than the device does)
only makes proofs harder, and the proofs exist, so tightness is low priority here.

A mismatch is brought to zhuominc, not filed as a library issue.

## What exists

| Test | What it compares | What it does not see |
|---|---|---|
| `claims/<kernel>/check_gpu.py` (41) | the real kernel, launched by its own host code on the `SETUP.md` launches and on edges of `Inst.ok`, against `Post` as stated: values bit for bit or within tolerance, negative tests showing the tolerance rejects wrong outputs, inputs unchanged, sentinel buffers around outputs | the **model**: a mistranscribed model whose proved `Post` still holds on the inputs tried passes; the **well-behavedness** predictions (no invalid access, no race): a kernel can read out of bounds and still produce the right output; **where** a failure comes from |
| `evidence/num-*` (15) | the device's results for the platform operations (`exp`, `/`, `tl.dot`, fp8 conversion, float atomics, reduction trees) against the accuracy facts | the `tl.*` definitions themselves |
| `evidence/float-layer` | the library's float definitions, compiled to native code, against the device, bit for bit | operations other than scalar floats, conversions and bytes; it was run on the previous library's `TVA.Math.Defs`, whose definitions are the same text as v3's (see below) |

No run logs of `check_gpu.py` are kept in the repository; the claims' READMEs quote some results.

### Evidence that refers to the previous library

Evidence READMEs name modules that are not in v3 (`TVA.Math`, `Rules.Num`, `Sem/`). The
inventory ([TRUST.md](TRUST.md)) found this is a matter of names: v3's float definitions
(`Base/Float`), `Int`, `DType`, `Bytes`, `Literal`, `Promote`, `Random` and the hints are the same
text as the definitions the evidence ran on, so the evidence applies to v3. What is missing is
evidence itself: fifteen folders of commit `5ea2115` (`literals`, `promotion`, `cdiv-round17`,
`permute`, `int-reductions`, `itof-rtz`, `fp8-constants`, `python-numbers`, `scalar-args`, six
`hint-*`) are not in the v3 tree, though v3's definitions rest on them.

## Phases

Phases 0 and 3 need no GPU. Phases 1, 2 and 5 need a GPU; phase 1's harness runs through the
executor (phase 3), and checks its own power without one (mutants, `--self`).

### 0. Trust inventory (no GPU): done, [TRUST.md](TRUST.md)

A table, `validation/TRUST.md`: for every `tl.*` definition in `TVA/Triton`, every field of
`Device`, and every claim, what validates it today: the Lean definition run on the device, a
Python reference, `check_gpu.py`, reading the compiler's source, or nothing. Includes the
mapping from each `Device` field to the evidence folder and the bound measured there. Its output
is the list of gaps, which orders the rest.

### 1. Each `tl.*` operation against the device (GPU; the harness runs without one)

The work is about the library, not only the 41 kernels: a kernel outside the examples uses
`tl.*` definitions no claim exercises. So the unit of coverage is the **operation**:
[COVERAGE.md](COVERAGE.md), generated by `coverage.py`, lists every `tl.*` operation of
`TVA/Triton` (121), what the executor does at it, and which cases and mutants run it.

`ops/` tests one operation at a time, through the executor (phase 3), so that what runs is the
library's own definition and not a copy:

- `cases.py` writes the cases: one operation, one dtype, inputs as bit patterns: the edge values
  (zeros, subnormals, extremes, infinities, NaN payloads; for integers `0`, `±1`, the extremes,
  shift amounts around the width), all pairs of them, random values; every pattern for the
  unary operations on 16-bit formats; `num_warps` 1, 4, 8 for reductions.
- `device.py` (GPU) runs each case as a Triton kernel whose only operation is the case's and
  records the output bits, with the stack it ran on.
- `Ops.lean` runs the definition with `exec` on the same inputs and compares lane by lane, with
  the relation the definition allows (equal bits; NaN against NaN for `upToNaN`; `MaxRel` itself,
  decided on the device's value, for `maximum`/`minimum`), never a looser one. Where the model
  predicts undefined behaviour the case is rerun lane by lane, and those lanes are counted, not
  compared. A reduction matches if one of a set of candidate trees gives the device's value
  (none matching is inconclusive).

Because a single-operation kernel's output *is* the value of the operation's choice, the
oracle can answer with it, and the definition's predicate is checked on the device's value:
this replaces, for single operations, phase 4's restriction to inputs where every choice agrees.
At a platform operation (`/`, `exp`, `tl.dot`, fp8) the oracle's answer is the device's output,
so the comparison holds by construction; such a case tests what surrounds the platform value
(shapes, element order, promotions), and the value itself is the device facts' (`evidence/num-*`).

**Mutants.** Each test is also run on wrong copies of the definition, as a transcription might
have them (subnormal results flushed, operands swapped, `fma` rounded twice, `//` rounding
toward −∞, `%` with the divisor's sign, arithmetic and logical shifts exchanged, `maximum`
propagating NaN, a float conversion rounding toward zero). `--self` uses the model's own outputs
in place of the device's, so that the inputs' power to tell each mutant from the definition is
measured without a GPU. Status (2026-11-13, `--self`, 85 cases): every mutant is caught on every
dtype where it differs from the definition; the three it is not caught on are equivalent there
(`//` and `%` on `uint32`, the exact conversion `f16 → f32`).

Still to add: the operations COVERAGE.md lists without cases (conversions `cvt`, `itof`, `ftoi`,
`cvtFrom8`, the reductions `max`/`argmax`/`histogram`, `where`, `reshape`/`permute`/`join`,
Philox, loads and stores with masks and `other`, atomics), and more mutants. The scalar float
layer's evidence (`evidence/float-layer`, against the previous library's identical text) stands;
rerunning it on v3's code is a cheap confirmation, not a priority.

### 2. Undefined-behaviour predictions, under `compute-sanitizer` (GPU)

Every covered launch is proved well behaved, so the model predicts: no invalid access, no race.
Run each claim's `check_gpu.py` unchanged under `compute-sanitizer --tool memcheck` and
`--tool initcheck` (and `racecheck`, which sees shared memory only, the compiler's own). Any
report on a covered launch is a finding. Add cases at the boundaries of `Inst.ok` where the
scripts do not already have them: a mask that ends exactly at the end of a buffer, a buffer of
exactly the required length, offsets at the edge of `int32`.

The cheapest phase with the most coverage: the 41 runners exist.

### 3. An executor for v3 models (no GPU)

`exec : Prog α → Mem → Oracle → Option (Res α × List Assumed)` runs one program on a concrete
memory, and `exec_sound` proves that whatever it reports (a final memory, or undefined
behaviour), `Step` can reach, provided every value it took without proof (the `Assumed` list,
platform sites only) satisfies its site's predicate. Nothing in it is trusted. It needs a change
to `Prog`, described in the next section. Done: `validation/Exec.lean` (`exec_sound`,
`execLaunch_sound`); the choice sites are in [PICKS.md](PICKS.md).

The launch is run one program after another, in grid order. For a tile-parallel kernel this is
one of the launch's interleavings; for kernels with atomics the order is the oracle's.

### 4. Each kernel's model against the device (GPU, needs phase 3)

For each claim, on small inputs taken from its `check_gpu.py`: run the model through `exec`, run
the kernel on the device, compare the final memories bit for bit. This tests the transcription
and the `tl.*` semantics together, on the actual kernels.

The model's choices are made so that the comparison is exact:

- platform operations (`exp`, `/`, `tl.dot`, fp8 conversion, float atomics): a **platform
  calibrated on the device**, `P_dev`, a table of the device's results, measured by separate
  kernels of one operation on the operands the run needs (two passes: record the queries, measure
  them, run again). Unary operations on 16-bit formats are tabulated whole once;
- free choices (reduction trees, lane order, disabled lanes' values): inputs for which every
  choice gives the same result (floats with small integer values make sums and `tl.dot` exact in
  any order; no NaNs), or `enable_fp_fusion=False` where fusion is the only freedom.

Order: the kernels with no platform operation and no float reduction first (`vec_add_f32`,
`kv_indices_i32`, `kv_cache_write_bf16`, `rejection_greedy_i32`, `vocab_embedding_bf16`,
`seeded_dropout_f32`, `count_expert_tokens_i32`), then the float kernels.

**Mutation checks on transcriptions.** Seed typical transcription errors into copies of a model
(an off-by-one mask, a swapped stride, a missing conversion, the wrong axis of a reduction) and
check that phase 4 catches each. This measures how much the tests say about item 2 of the
trusted base, which today is checked by reading.

A mismatch in phase 4 that is not a bug: `P_dev` assumes the device computes an operation inside
the kernel as it does alone. If, for example, fusion inside the kernel changes `tl.exp`'s result,
the test fails while the model (a relation per element) allows it. Such a mismatch is localised
by instrumenting the kernel (extra stores), which is fine for localising and not for testing:
instrumenting changes what Triton compiles.

### 5. Atomics across programs (GPU)

Several claims use atomics (`streamk_matmul_f16`, `lora_shrink_bf16`, `route_histogram_i32`,
`count_expert_tokens_i32`). Litmus tests of what `TVA.Launch` allows (message passing, store
buffering, coherence on one cell), and of the argument of `MemSem.unused`: an atomic whose result
is unused behaves as `acq_rel` at `gpu` scope, whatever its `sem`.

## The change to `Prog` that phase 3 needs

### The problem

`Prog.pick P k` stores the predicate `P : β → Prop` and the continuation `k`. To run it, an
executor must produce some `b` with `P b` and continue with `k b`. In compiled code `P` is
erased (it is a proposition), and so is `β`: at run time the executor sees a `pick` node and a
closure, and cannot tell an `upToNaN` from a reduction tree or a bounds guard. It can neither
build a witness nor check one, and an oracle cannot answer a question it cannot see.

Recording the values from the device instead does not work: most `pick`s have no value on the
device (a guard picks `()`; the tree of a reduction is the shape of the computation, not a value;
the order in which a store's lanes land), recording a value that exists changes what Triton
compiles, and a recorded bit pattern still has to be given to `k` at an erased type.

### The proposal

Each `pick` carries a solver, which the semantics ignores:

```lean
| pick (P : β → Prop) (solve : Solve P) (k : β → Prog α) : Prog α

/-- A certified answer to "some `b` with `P b`". -/
inductive Ans (P : β → Prop) where
  | ok    (b : β) (h : P b)     -- a witness, with its proof
  | empty (h : ∀ b, ¬ P b)      -- no witness: undefined behaviour

structure Solve (P : β → Prop) where
  run : Hints → Option (Ans P)  -- `none`: no answer, the executor gives up
```

The solver is written next to `P`, by whoever writes the `pick`, in `TVA/Triton` (no claim
contains a `pick`). At each site it either computes the witness or asks the oracle a typed
question from a closed family that survives compilation, and returns the answer with its proof:

| Kind of site (examples) | Solver |
|---|---|
| guards: block pointers, descriptors, `tl.assume`, `static_assert`, conversions' conditions | decides the condition; `empty` is a predicted undefined behaviour |
| compiler hints: `multiple_of`, `max_contiguous`, `max_constancy` | the witness is the value itself, if the hint's condition holds |
| partial functions: integer `//`, `%`, shifts | the only candidate, or `empty` |
| `upToNaN`, IEEE operations, `maximum`/`minimum`, `addc`/`mul_add` without fusion | the IEEE result |
| free choices: reduction and scan trees, `sort`, `histogram`, `reshape(can_reorder=True)`, disabled lanes, padding | asks the oracle (`Query.tree n`, `Query.perm s`, `Query.val d`, …), then evaluates `P` on the answer |

Platform operations are written `env fun e => pick (fun r => e.P.math .exp f x r) k`: `P`
mentions the platform `e.P`, which is a variable, so no solver can produce or check a result.
Their solvers assume the oracle's answer instead (next section); `Prog.plat q k`, with
`q : PlatQ` the operation on its operands (`math`, `div`, `cvt` into fp8, `dot`, `dotScaled`),
is the abbreviation for this pattern. (A first version made `plat` a constructor of `Prog` with
its own `Step` rules; it was replaced by the definition.)

### Assumed answers: sites whose predicate mentions the platform

Some sites mix a platform relation with something else, so neither a solver nor `plat` can answer
them: `dot_add` and `dot_scaled_add` (`tl.dot(a, b) + c`: the platform's dot with `c` folded in,
or the dot followed by a fusable addition), a float `atomic_add` (the update is
`e.P.atomicAdd`), a conversion into fp8 inside `tl.convert`. Certifying them would mean
restructuring the definitions (the first two would become a choice of branch, then `plat`, which
changes when undefined behaviour is reachable, and eight proofs). Instead:

- `Ans` has a third answer, `assume b`: a value with no proof. `Solve.assume q` asks the oracle a
  question `q` that carries the operands (`Query.plat`, `Query.convert`, `Query.atomicAdd`) and
  assumes its answer. `Step` ignores solvers, so meaning and proofs are unchanged.
- `exec` returns, with its result, the list of values it took without proof (`Assumed`: the
  site's predicate and the value); `exec_sound` and `execLaunch_sound` are conditional on each of
  them satisfying its predicate.
- The oracle does not choose one implementation: it answers each question with the device's value
  for those operands (a single-operation kernel's output; in phase 4, `P_dev`, the same operation
  run alone). What is then to check is that the device is explained by *some* platform
  satisfying `Device`: take the platform whose relations are the logged answers (each assumption
  then holds by construction) and check it against the device facts at the logged operands, for
  example each `exp` result within `ExpF32`'s bound. That check is per value and decidable.
- `dot_add`'s solver puts the device's value in the first branch (the dot with `c`). If the
  device instead computed the dot and then added, the value may miss the dot's bound and the
  check fails: a false alarm, which needs the unfused product to resolve, and a single-operation
  kernel cannot observe it.
- Open: if the device gives two answers for the same operands at different sites, the platform
  built from the log is a relation, not a function; whether some `Device` field requires
  determinism is to check.

**`plat` is a definition, not a constructor** (2026-11-13). `Prog.plat q k` is
`env fun e => pick (q.Rel e.P) (Solve.assume (.plat q)) k`: the old `env`-then-`pick` pattern,
with a solver that assumes the oracle's answer. So `Step`, `Safe` and `SafeA` have no `plat`
case (`Safe.plat` and `SafeA.plat` are theorems, from `env` and `pick`, with the statements the
constructors had), no proof outside `lean/TVA/Program.lean`'s solvers changed, and the change
to `Prog` is: a solver field on `pick` and on `rmw`, and the answer `Ans.assume`.

### What it costs and what it does not change

- **Meaning: unchanged.** `Step.pick` ignores `solve`; `Prog.plat` unfolds to the old pattern.
  A reader of a claim can ignore solvers. A wrong certified answer cannot be built, since it
  carries its proof, so a wrong solver can only make the executor give up or assume a value; and
  every assumed value is reported, so `exec_sound` holds for every solver and every oracle, under
  the reported assumptions.
- **Claims: no statement changes.** No claim file contains `pick`. Whether the claims' sha256
  change depends only on whether the claim files change, which they need not.
- **Proofs.** No rule and no oracle proof changes: `Safe.plat` and `SafeA.plat` are theorems
  with the statements the rules use. All 41 oracle proofs check unchanged.
- **Size.** 68 `pick` sites in `TVA/Triton`, each given a solver (most are one word:
  `Solve.guard`, `Solve.ok v rfl`); about a dozen platform sites (in `Arith`, `Convert`, `Dot`) are written `Prog.plat`.

### Alternatives considered

- **A copy of each model that the executor can run**, in `validation/`, with a proof that it
  equals the original. No library change, but 41 copies to keep in sync and to prove equal.
- **An executor over Lean's syntax trees** (`Expr`), recognising each `pick` by the shape of
  its `P`. No library change, but slow (models build tensors of thousands of elements) and tied
  to how each definition happens to be written.
- **No executor**: phases 0–2 and 5 only. The transcriptions stay checked by reading and by
  `check_gpu.py`.

## Scope, and the compiler's hidden parameters

**Scope.** A claim is about one stack: an H200 (sm_90), Triton 3.8.0, the CUDA toolchain and
driver of the evidence (torch 2.11.0+cu130, driver 610.57). `Device`'s docstring says so; the
claims do not. Other GPUs or versions are out of scope for now: they would need their own
`Device'`, and the `Platform` signature itself is untested beyond sm_90 (below).

**Hidden parameters.** Within that stack the compiler's output depends on settings that the
model does not name. Soundness needs each to be *covered*: modelled, absorbed by a free choice
whose bound the evidence measured across the setting, or pinned. Status to be completed (`?`:
not yet checked):

| Setting | How the model covers it | Varied in the evidence |
|---|---|---|
| `enable_fp_fusion` | modelled (`Env`) | fusion itself: none (TRUST.md) |
| `input_precision`, `max_num_imprecise_acc` | modelled (`DotCfg`) | ? |
| tile shapes, other constexprs | part of the kernel | partly (`num-dot-int8`: 14 configs) |
| `num_warps` | free: reduction trees, `tl.dot`'s chunking | `reduce-tree` 1–16; `num-dot-int8`; `num-dot-chunk` 4 only |
| MMA instruction (`mma.sync` vs `wgmma`, chosen from `M`, `num_warps`) | free | `int8` both; float dots ? |
| `num_stages`, `maxnreg`, `num_ctas`, cluster dims | assumed not to change values | ? |
| surrounding code (fusion, rescheduling of `exp`, `/` inside a kernel) | relation per occurrence | none: measured standalone |
| flush-to-zero defaults | stated in the facts (`ExpF32`, `SqrtF32`, …) | yes, `num-math-f32` |
| environment variables (`TRITON_F32_DEFAULT`, …) | ? | ? |
| autotuning (config picked at run time) | must fall inside `Inst.ok` | ? per claim |

Each `?` is settled by reading the lowering or by varying the setting in the existing harnesses
and checking the bounds still hold. A setting that cannot be covered is pinned in the claim.

**Generality (later, no GPU).** Whether the `Platform` signature is the right cut beyond sm_90
can be checked on paper: for another target's lowering (Blackwell, AMD), is every operation
whose result differs from the IEEE one among `Platform`'s fields, or is some operation that
`TVA.Base` treats as exact (subnormals in `+`/`*`, `div_rn`, conversions) lowered differently?
