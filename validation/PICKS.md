# Choice sites, and how `exec` answers them

The semantics is written for any signature `Sig` (`TVA.Program`): the values a program cannot
predict (sites), what each allows (`Sig.Allows`), and atomic updates (`Sig.Upd`,
`Sig.UpdAllows`). Triton's signature is the catalog `TVA.Site`. `Step.pick` continues with any
allowed value, and the library runs no solver. The solvers live here, in `validation/`.

## The catalog

There is one constructor per semantic family, not one per `tl.*` function. Add a constructor
only when the allowed-result relation, or the run-time data a solver needs, differs from an
existing one.

- A constructor carries **executable** data, enough to produce or check a witness: a `Decidable`
  instance, a lanewise partial function, or the operands of a platform request. It never carries
  an erased predicate.
- It carries **only** what its relation needs. Run-time bookkeeping (occurrence numbers, solver
  settings) lives in the executor's records.
- `Site.other β P` is for relations that have no family yet. The executor reports them as
  unsupported.

**Changes preserve meaning.** For every operation, the new `Allows` is equivalent to the
predicate it replaced, so the allowed results and the cases of undefined behaviour are both
unchanged (`Preserve.lean`, mostly `Iff.rfl`). The semantics sees a site only through its relation
(`TVA.Launch.Erase`), so the meaning of every kernel is unchanged.

- A mixed operation stays one site with its disjunctive relation (`dotAdd`: the platform dot, or
  the fused form). Splitting it into a free branch choice followed by an operation adds undefined
  behaviour through an empty branch.
- Where the semantics compares programs (`Step.defer`, `UsesSharedAtomicResult`), it compares
  their erasures (`Prog.erase`): each site and update replaced by its relation. Data a constructor
  carries but its relation ignores is therefore never a dependence, as in v3.

## Solvers (`Solve.lean`, `Solvers.lean`)

`instance Site.solvers : Solvers` gives one solver per `Site` and `Upd` constructor. A solver
returns an `Ans`, which is one of:

| `Ans` | meaning |
|---|---|
| `ok b h` | a value, with a proof that the site allows it |
| `empty h` | a proof that the site allows nothing: predicted undefined behaviour |
| `none g` | a gap (`Gap`: `unsupported`, `searchFailed`, `badAnswer`, `noOracle`); never undefined behaviour |
| `assumed b` | an unproved value, only at platform-dependent sites (`sitePlatform`, `updPlatform`) |

When a solver cannot compute something, it asks the oracle a typed question (`TQuery`: a tree,
a lane order, an element, a platform result, a conversion into fp8, a float atomic add). The
oracle is indexed by occurrence number, so repeated requests can get different answers.

**A supplied answer that does not fit the request is `badAnswer`; it is never replaced by a
default.** Examples are a tree that does not cover the leaves or breaks the depth bound, and a
lane order that is not a permutation. A default is used only when no answer was supplied.

How each family is answered:

| sites | answer |
|---|---|
| `guard`, `hint` | decided; false is a predicted undefined behaviour |
| `lanes` (`//`, `%`, shifts) | computed, lane by lane; a lane with no value is `empty` |
| `upToNaN`, `maxMin`, `fromF8`, `ftoi`, `histogram` | the exact value |
| `addc`, `mulAdd` | the unfused IEEE value. A fused device result is not it, so run with `enable_fp_fusion=False` or pick inputs where both agree |
| `itof` | the direct rounding |
| `convert` | computed for every pair of dtypes; into fp8, the oracle's value (assumed) |
| `plat`, `dotAdd`, `dotScaledAdd` | the oracle's value (assumed) |
| `fsum*`, `fmax*`, `arg*` | the oracle's tree, else the sequential tree, else the balanced one, checked against `Covers` and the depth bound |
| `sumBcastMul` | the oracle's tree; else the oracle's dot (assumed); else the sequential tree |
| `pad` | zero, the all-ones NaN pattern, or for `.undef` the oracle's element |
| `anyVals`, `order` | zero bits; the oracle's lane order if it is a permutation, else index order |
| updates `xchg`, `cas`, `max`, `bit`, integer `add` and `red` | computed |
| float `add` and `red .add` | the oracle's value (assumed) |
| `other` (scans, `sort`, `reshape_any`, `make_tensor_descriptor`) | unsupported |

Per operation: [COVERAGE.md](COVERAGE.md), generated by `coverage.py`.

## Freedom outside sites

- `load`: the values of disabled lanes come from a `Fill`, outside the oracle.
- `store`: lanes land in index order (this only matters for duplicate addresses).
- `Step.defer`: `exec` never defers. This is sound, but it explores only one order.
- The launch: `execLaunch` runs the programs one after another in grid order. That is one
  interleaving.

## The executor (`Exec.lean`) and what it claims

`exec` is total. It returns `Res` (`done`, `ub`, `stuck occ gap`, or `outOfFuel`) together with
a `Record` for every request it answered.

- `exec_sound`: a `done` result is reached by `Runs`, and a reported `ub` is a `Runs` to a step
  whose outcome is `ub`. Both hold provided the assumed records hold (`Record.Assumptions`).
- `execLaunch_sound` is the same for a launch, as a `Reach` from `Config.start`.
- `stuck` and `outOfFuel` claim nothing.

Neither theorem says anything about races (`WellBehaved`), and completeness is not claimed.

Memory is a hash table (`CMem`), read through `CMem.toMem`. Tensors are still functions, so a
long-looping kernel may need memoised tensors.

## Verdicts (`Verdict.lean`)

| verdict | meaning |
|---|---|
| `certified` | agreement, with every answer proved (`ofRes_certified`, `ofLaunch_certified`) |
| `conditional n` | agreement that rests on `n` assumed platform answers (`ofRes_conditional`) |
| `discrepancy` | a candidate finding: one run of the model disagrees, or predicts undefined behaviour (`ofRes_discrepancy`). Bring it to zhuominc |
| `inconclusive` | a failed search, a bad or missing oracle answer, or no candidate agrees |
| `unsupported` | no solver, or out of fuel |

## Running it

After `lake build TVA TVA.Proof` in `lean/` (or with `$TVA_LEAN` pointing at a built `lean/`):

```sh
python3 validation/run_test.py vec_add_f32 solvers           # the tests in validation/tests/
python3 validation/run_test.py --ops CASES --self RESULTS    # single operations and mutants, no GPU
python3 validation/coverage.py                               # regenerate COVERAGE.md
python3 validation/check_oracles.py OUT_DIR [KERNEL ...]     # every oracle proof; exits 1 on a failure
```
