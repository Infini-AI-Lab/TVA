TVA: AI Agents Prove Triton Kernels Correct

TVA is a Lean 4 library for proving Triton kernels correct, with a sandbox in which AI agents write the proofs. A proof covers every launch a claim allows: no fault, no race, no write outside the outputs, and every output within a stated bound of the exact result.

Zhuoming Chen · InfiniAI Lab, Carnegie Mellon University · November 2026
Code on GitHub ↗

The inference stack is under attack

  • Inference providers. Fireworks AI disclosed misuse of internal credentials in October 2026, then a second intrusion through a third-party cloud provider. Its November update adds account data and, for some customers, secrets, datasets and incomplete model weights (Crypto Briefing, Dr. Web).
  • Serving engines. SGLang's CVE-2026-5760 (CVSS 9.8) lets a chat template inside a GGUF model file run code on the server; two critical deserialization flaws preceded it (The Hacker News, CSA).
  • The supply chain. A malicious intercom-php release and a compromise of the Laravel-Lang packages shipped credential stealers and backdoors through the projects' own release channels (Cloudsmith, The Hacker News).

None of these went through a GPU kernel, but they share a pattern: attackers target code that is trusted, changes fast, and is too large to re-read. Kernels fit. vLLM and SGLang together contain about 1,800 @triton.jit functions, each new model architecture adds more, and agents now write many of them. A kernel can read and write all of GPU memory, including the weights and every request's KV cache, and its bugs are silent: an int32 offset that wraps past a few million tokens, an off-by-one mask, or a race returns a plausible wrong answer or reads another request's data. Researchers have also built backdoors that trigger only under particular compiler optimizations or hardware (1, 2).

Tests sample a few shapes and inputs, and review cannot keep up with the rate of change. A machine-checked proof covers every launch the host can make. Writing such proofs by hand costs too much, so nobody does it for production kernels. We bet that agents can.

What TVA is

  1. A Lean 4 semantics of Triton (about 8,300 lines): tensors, the tl.* operations, masked loads and stores, atomics, and a launch as programs interleaving over a byte-addressed memory. Floats are exact IEEE bit patterns (fp32, fp16, bf16, fp8, mxfp8 with e8m0 scales) with exact rounding; integers have fixed width and wrap. Where the hardware leaves a result open (tl.exp, the order of a tl.dot accumulation, float atomics), the operation returns any value a device fact allows, and each device fact rests on our measurements on an H200.
  2. A proof kit (about 16,000 lines of proved lemmas) for memory access patterns, loops, integer widths, floating-point error, tl.dot accumulation, online softmax, decayed recurrences, scans and shared atomics. A proof walks the kernel one program at a time.
  3. A sandbox for agents: a container with the library, its docs and one tool that grades a proof.

Stating a claim

A claim, written once by hand and pinned by its SHA-256, transcribes a kernel line by line into TVA's vocabulary and says which launches it covers and what each must leave in memory. Inst is what the host chooses (shapes, scalars, buffers), ok the covered choices, Post the required final memory: 

def Claim.Holds (c : Claim) : Prop :=
  ∀ P, Device P →                    -- every platform with the H200's device facts
  ∀ d, c.ok d →                      -- every covered launch: shapes stay symbolic
  ∀ init, c.Pre d init →             -- every initial memory, including the data
    Correct (c.kernel d) (c.launch d) init (c.Post d init)
-- Correct: no undefined behaviour, no race between programs, and every way the launch can end
-- is a normal end (no fault, no hang) whose final memory satisfies Post.

The model of Triton's vector-addition tutorial, one line per source line: 

def add_kernel (x_ptr y_ptr output_ptr : Ptr .f32) (n_elements : I32) (BLOCK_SIZE : Nat) : Kernel where
  body ctx := do
    let pid := tl.program_id ctx 0
    -- `pid * BLOCK_SIZE` is computed in int32, and wraps
    let block_start := pid * (IntV.ofNat BLOCK_SIZE : I32)
    let offsets := block_start + tl.arange 0 BLOCK_SIZE
    let mask := offsets.ltS n_elements
    let x ← tl.load (x_ptr + offsets) (some mask)
    let y ← tl.load (y_ptr + offsets) (some mask)
    let output ← tl.add x y
    tl.store (output_ptr + offsets) output (some mask)

Its Post says that output element j < n is the IEEE sum of the inputs' elements j, and that every other byte is unchanged. Every claim has that last clause, so a proved kernel writes only its outputs.

For production kernels, the conditions carry most of the content. SGLang's 50-line vocabulary embedding lookup needs eleven, none written in its source: the ids are int32 or int64, BLOCK_H is a power of two, the int32 column index cannot wrap, the grid fits CUDA's limits, every vocabulary index of the tensor-parallel shard fits in int64, and the output shares no byte with the inputs. A reader can check each against the host code. For floating-point kernels, Post bounds the error against the exact real-number result, with a tolerance derived from the device facts that stays meaningful at the largest covered size.

What you trust

One file lists it: Lean and Mathlib; that the model transcribes the kernel; that Triton 3.8.0 compiles the kernel as the model says, outside a published list of 56 exclusions (known miscompiles among them); and the device facts with their measurements. Lean checks everything else, including the proof kit and every agent-written proof.

Agents prove, a machine grades

Because the claim is fixed, nobody has to judge the agent's proof. The agent gets one claim in a container, as a Harbor task, with the built library, its docs and one worked example. It writes theorem main : claim.Holds and builds as often as it likes. A grader in a separate container then checks that:

  1. the claim file is byte-for-byte the pinned one;
  2. the proof has no escape hatch: no sorry, axiom, native_decide, implemented_by, meta code, local instances or foreign imports;
  3. everything builds from scratch;
  4. main has exactly the type claim.Holds and uses only Lean's three standard axioms;
  5. Lean's kernel re-checks every declaration of the claim and the proof.

The result is a reward of 1 or 0. Each claim also has a reference proof, which the agent never sees: a task gets only the claim's own files, and the agent's container reaches no network but the model endpoint.

Results: agents proved all 41 claims

We used TVA to write fixed claims for 41 kernels. Fourteen are Triton tutorial and library kernels: vector addition, softmax, layer norm, fp16, fp8 and mxfp8 GEMMs, persistent and TMA GEMMs, stream-K with atomics, FlashAttention forward and backward, and paged attention. Twenty-seven are production kernels, 12 from SGLang, 7 from vLLM and 8 from flash-linear-attention: extend and prefill attention over paged and variable-length batches, fused MoE, LoRA, int8 scaled GEMMs, speculative-decoding rejection sampling, KV-cache writes, and Mamba-2 SSD and gated DeltaNet chunked recurrences.

All 41 now have complete proofs written by AI agents, each accepted by the grader in a fresh container: 40 by Claude Sonnet 5.5 agents, plus the vector-addition worked example. The hardest took several agent sessions, each handing a written plan to the next.

Proof size follows the reasoning a kernel needs, not its length. Elementwise and gather kernels are short. GEMMs need the error of a tl.dot accumulation over the K loop. Attention needs an online-softmax invariant whose error bound survives every rescaling; linear attention needs a state invariant carried across chunks with decays. SGLang's extend attention, with a paged KV cache, tree masks for speculative decoding and sliding windows, took 49 modules.

Volta checks an optimized kernel's equivalence to a reference by symbolic execution, with thread counts, tensor sizes, pointer targets and branch conditions known statically, and compares expressions over the reals; its open implementation, ptx_verifier, extracts Lean propositions for a fixed size. SentryWard verifies synchronization, race freedom and equivalence of warp-specialized Hopper and Blackwell kernels at fixed sizes, without data-dependent addresses or branches. Formalizing PTX in Lean models every execution of hand-written PTX under the PTX memory model, including asynchronous copies and tensor cores, with LLMs writing the proofs. GPUVerify and Faial prove race freedom only; ProofWright and Browne et al. target elementwise kernels or a CUDA subset.

TVA works one level higher, on Triton, and trusts the Triton compiler under one stated rule. In return it covers what serving kernels do: shapes known only at run time, addresses read from memory (page tables, expert maps, sequence offsets), integer arithmetic that wraps, and floating-point results that differ from the exact answer. A real-number equivalence proof cannot say how far a bf16 attention output may be from exact attention at long context; a TVA claim states that bound and the proof establishes it.

Limits

  • The Triton compiler is trusted outside the exclusion list, and claims target one stack: Triton 3.8.0 on the H200.
  • Claims are written by hand, and a reader must check that each model transcribes its source; the line-by-line form keeps that check local.
  • A proof guarantees only what its claim states. Each claim lists the launches it leaves out, such as in-kernel TMA descriptors.
  • Proofs are long, and agent time costs money.

What's next

The 41 claims and the grader form a benchmark: one kernel and one fixed claim per task, scored by a binary machine check that weakening the specification cannot game. We are using it to compare models, and working toward agents that answer a wrong kernel with a concrete launch that breaks it. TVA and the claims are open source at github.com/Infini-AI-Lab/TVA.
