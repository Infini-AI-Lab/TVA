#### F1

**ASSUMPTION_FALSE** on `item:assumption:exp2Acc` (blocking): tl.math.exp2 compiles to ex2.approx.ftz.f32 (libdevice __nv_exp2f under reflect FTZ), which flushes results below 2^-126 to +0, so the absolute term 2^-149 is false: at x = -127 the error is 2^-127.

Lowering. math.exp2 does not reach the NVPTX fexp2 pattern the docstring cites. TritonGPUToLLVM.cpp:195-197 (third_party/nvidia/lib/TritonNVIDIAGPUToLLVM, in the Triton 3.8.0 source tree) registers populateMathToLLVMConversionPatterns and populateGpuToNVVMConversionPatterns together. The scalar math.exp2 becomes a call of libdevice __nv_exp2f. libdevice picks llvm.nvvm.ex2.approx.ftz.f32 when __nvvm_reflect("__CUDA_FTZ") is 1, and Triton sets that flag by default (enable_reflect_ftz = True, triton-3.8.0-nvidia-compiler.py:122, 455-456). The PTX ISA says .ftz flushes subnormal inputs and results to sign-preserving zero.

Counterexample to the Lean statement. Take x = -127. It is finite, in dom = univ, and the room condition holds. The device returns +0, so the error is |0 - 2^-127| = 2^-127, which is above 2^-22*2^-127 + 2^-149.

The kernel reaches such inputs. Both qk*c - m_ij and m_i - m_ij go down to about -2*Mmu, for example about -522 at HD=128, R=4, c=0.128. another project's exhaustive survey measures the flush: 0.999994 of a 2^-126 bound at the input just below -126 (another project docs/rules/num/ex2approx.md, Evidence).

What would resolve it:
- Err.absE := 2^-126, which is another project's Ex2FtzCard (exhaustive conformance pass on H200 NVL).
- Correct the lowering text in the docstrings of exp2Acc, Err.absE and exp2NegInf, and in docs/examples/flash-attn-fwd.md:143-145. The fact -inf -> +0 also holds for the .ftz form, so exp2NegInf's statement stays.
- With absE = 2^-126 the error constants change negligibly. I re-evaluated errO and errM at N=131072, HD=128, R=8: the same to 4 digits. Platform.ref still witnesses the weaker rule.

*Evidence:* Triton 3.8.0 / sm_90 compiles of this kernel (tutorials/06-fused-attention.py) are in the user's cache. Each _attn_fwd.json gives triton_version 3.8.0 and arch sm90.
- ~/.triton/cache/JV7H2PWPDMNNJZP7VB7D4MWMMM745GODD7ZVG3JWO5Q4QTHZLBQA/_attn_fwd.llir:421-450 has __nv_exp2f inlined, with the __nvvm_reflect branch between ex2.approx.ftz.f32 and ex2.approx.f32.
- The PTX of that compile has 18 ex2.approx.ftz.f32 and 0 ex2.approx.f32.
- The other three compiles give the same picture: AZQJBXVI... (36 vs 0), JNA4UMWX... (132 vs 0) and 45MGVVPP... (264 vs 0).

**EVIDENCE_REQUEST** on `item:assumption:faithful` (blocking): Inst.ok covers HEAD_DIM=256 with BLOCK_N=128, which does not fit sm_90 shared memory under any of the tutorial's configs. It also covers HEAD_DIM=256 with BLOCK_M=128 at 4 warps, which needs at least 256 accumulator registers per thread. Show compile logs or narrow Inst.ok.

Shared memory, measured. The cached Triton 3.8.0 compile with BM = BN = HD = 128 and num_stages = 2 (JNA4UMWX.../_attn_fwd.json, shared = 163872) uses 5 x 32 KB + 32 B. So q has one buffer and k and v have two each.

Shared memory for HD=256 and BN=128:
- the k and v buffers alone take 4 x 128*256*2 B = 256 KB;
- that is above 227 KB (232,448 B), the sm_90 per-block maximum;
- this holds for every num_stages in NUM_STAGES_OPTIONS = [2, 3, 4], with either BM.

Why this matters. The autotuner drops such configs (OutOfResources), so the instance never launches. The rule page says a launch that fails is a fault. Then `faithful` is false for those d, so Assumptions K P fails for the real device as a whole, and main gives nothing even for the instances that do compile.

Registers. For HD=256, BM=128 and BN <= 64, `keep` leaves only num_warps=4 on Hopper, because BM*BN < 128*128. The 128x256 fp32 accumulator is then 256 registers per thread, above the 255 limit. I could not tell whether wgmma with such an accumulator compiles.

What would resolve it, either of:
- compile logs of the largest covered instances: HD=256 with each (BM, BN), and HD=128 with (128, 128);
- restrict Inst.ok to what compiles, for example BN*HD <= 2^14, and BM*HD <= 2^14 unless a log shows otherwise.

#### F5

**ASSUMPTION_FALSE** on `item:assumption:faithful` (blocking): On the tutorial's default Hopper path (warp_specialize=True) the kernel builds its descriptors with tl.make_tensor_descriptor and writes them to global scratch, 512 B per program. The model never writes that memory, so Faithful (the device's final memory is some model final memory) and Post's frame are false as stated.

Which path the tutorial takes. forward defaults to warp_specialize=True (line 508). On Hopper, line 525 then passes the raw tensors, and _maybe_make_tensor_desc (lines 169-173, 197-208) calls tl.make_tensor_descriptor. The bundle covers this path explicitly: the attn_fwd docstring says the kernel may build the descriptors itself. triton.set_allocator(alloc_fn) (lines 545-548) provides fresh torch memory per launch.

What the device does. The cached compile (JV7H2PWP...) shows:
- 4 x ttg.global_scratch_alloc of 128 B (ttgir:43-55);
- global_scratch_size 512 in the json;
- the PTX writes each tensormap into that memory with tensormap.cp_fenceproxy.global.shared::cta.

Why that contradicts the claim. TVA.Mem is global memory. Faithful requires the device's fin to be a model outcome, and the model leaves those bytes unchanged. Post also says every byte outside o and M is unchanged. Desc.lean:36-37 says only that the model assumes the scratch does not overlap the kernel's buffers.

What would resolve it, either of:
- preferably, a library statement (Lang/Desc.lean, docs/rules/compiler-faithful.md) that the launch's runtime scratch is outside the memory Faithful compares and frames speak of. That covers the set_allocator buffer and Triton's global and profile scratch, which are fresh per launch and disjoint from Pre's buffers. This is library-wide and may be better handled as a library fix;
- narrow this bundle to host descriptors (warp_specialize=False).
