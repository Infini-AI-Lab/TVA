#### F2

**LIBRARY_REPORT** on `decl:TVA.tl.make_tensor_descriptor` (non-blocking): Does the evidence behind in-kernel descriptors cover descriptors rebuilt inside a runtime loop, rewriting a program's scratch slot while TMA stores through the previous one may be in flight?

SEMANTICS.md (Tensor descriptors) makes tl.make_tensor_descriptor pure in the model and leaves the scratch to Compiler.Faithful (scope 5), trusting TMA's asynchrony to the compiler. evidence/desc-scratch exercises straight-line kernels that build their descriptors once; its sources say each make_tensor_descriptor op has one scratch slot per program (no reuse across ops). Tutorial 08's grouped_matmul_tma_kernel builds a_desc, b_desc and c_desc inside the runtime if of line 220, once per trip of the loop of line 212, so a program rewrites the same three 128-byte slots for group g + 1 right after its last c_desc.store of group g, an asynchronous TMA store through the old descriptor. Whether Triton 3.8.0 orders that rewrite after the store has read its descriptor is the compiler's; no evidence I found runs this pattern. Not blocking: I took the library as right. A probe (a loop that rebuilds a store descriptor with a new base on every trip, checking every output) or a statement in SEMANTICS.md would settle it.

But `OutSpec` bounds the stored float16 `c` by tol + (|S| + tol)·2^-11 + 2^-25, so with products of one sign Post allows a relative error of (1 + rho)^T - 1 + (1 + (1 + rho)^T - 1)·2^-11: 0.253% at K = 2^13. That still rejects a bfloat16 rounding at every covered K (work/tol.py: at K = 8192, rows of ones against 8160 ones and 32 twos give S = 8224, exact in float32 and float16; Post allows |c - S| <= 20.79, and the bfloat16 rounding 8192 is 32 off), so the claim is not affected. The threshold the README names is where the accumulation part alone reaches 0.389% (T = 245, K from 15617, work/tol.py); Post's whole bound on c reaches it at T = 214, K from about 13633. To resolve: give Post's whole relative bound (0.253% at 2^13) in the comparison, and the threshold as about K = 13.7k, or say that 15745 counts the accumulation only.

*Evidence:* work/tol.py (exact rationals): rho = 1.5914e-05; (1 + rho)^T - 1 = 3.18e-05, 2.55e-04, 2.039e-03 at K = 128, 1024, 8192; with the float16 rounding 5.20e-04, 7.43e-04, 2.528e-03; bfloat16 worst 3.891e-03; accumulation alone reaches it from K about 15680 (T = 245), the whole bound from K about 13696 (T = 214).

#### F4

**LIBRARY_REPORT** on `lib:docs/rules/compiler-faithful.md` (non-blocking): Scope 5 (descriptor scratch) says nothing of the scratch's alignment, though the launcher passes the allocator an alignment that the tutorial's alloc_fn ignores

Scope 5 covers a launch whose allocator returns a buffer that holds none of the launch's bytes and that nothing else writes during the launch. The allocator is called as alloc_fn(size, alignment, stream) (source lines 317-318 show the signature), and each program writes its descriptors into that buffer for TMA to read. Tutorial 08's alloc_fn ignores `alignment` and returns torch.empty(size, dtype=torch.int8), which PyTorch's caching allocator happens to align; an allocator that meets scope 5 as written but returns a misaligned buffer (an offset slice of a larger one, say) is not excluded, and the rule then promises no fault. This kernel's host is not affected. Should scope 5 also ask that the buffer have the alignment the launcher requests (or the page state, with evidence, that a misaligned scratch is harmless)?
