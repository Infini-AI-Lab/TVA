#### F1

**EVIDENCE_REQUEST** on `item:assumption:faithful` (blocking): Faithful is assumed for every power-of-two BLOCK up to 2^20, but nothing shows that the largest covered instance compiles and launches. One failing instance makes Assumptions false for the real device on every instance.

Inst.ok (examples/TVAExamples/VecAdd.lean:68-71) admits every power-of-two BLOCK <= 2^20. The host uses only BLOCK_SIZE=1024 (tutorials/01-vector-add.py:75). With Triton 3.8.0's default num_warps=4 (third_party/nvidia/backend/compiler.py:111), BLOCK=2^20 gives each thread 8192 f32 elements of each of x, y and output, plus 8192 64-bit pointers per pointer tensor and the mask bits. Triton emits all x loads, then all y loads, then the adds, then the stores, so ptxas will probably spill to local memory, and the driver must reserve that local memory for every resident thread at launch. Either step may fail: a ptxas error ('uses too much local data', or out of memory during compilation), or a launch error (no memory left for local memory). docs/rules/compiler-faithful.md counts such a failure as a `fault`, for every init on that instance, so `Rules.Compiler.Faithful P (model d) (launch d) (K d)` is false for that d. The field `faithful` is quantified over all d with d.ok. So a single failing covered instance makes `Assumptions K P` false for the real device K, and then `main` says nothing about any instance, including the host's BLOCK=1024. compiler-faithful.md says the rule is accepted only for instances that compile and launch, and REVIEWER_GUIDE §3 asks for a compile log of the largest covered instance when in doubt.

To resolve, do one of the following:
(a) give a Triton 3.8.0 compile log for add_kernel with BLOCK_SIZE=2**20 on the target GPU (ptxas -v: registers, spill stores and loads, local bytes per thread), and a launch with n >= 2^20 that runs to completion and gives correct results;
(b) narrow Inst.ok to BLOCK <= 2^k for the largest k that has such a log (1024, the host's value, is enough for the tutorial), and list the narrowing in docs/examples/vec-add.md.

*Evidence:* examples/TVAExamples/VecAdd.lean:71 `(∃ e, d.BLOCK = 2 ^ e) ∧ d.BLOCK ≤ 2 ^ 20`; VecAdd.lean:109 `faithful : ∀ d, d.ok → …`; tutorials/01-vector-add.py:75 `BLOCK_SIZE=1024`; triton-3.8.0 third_party/nvidia/backend/compiler.py:111 `num_warps: int = 4`; docs/rules/compiler-faithful.md 'A launch that fails is a fault, so the reviewer accepts the rule only for instances that compile and launch.'

#### F2

**DOC** on `decl:TVAExamples.VecAdd.Inst.ok` (non-blocking): `n + BLOCK ≤ 2^31` is stricter than int32 indexing needs. The docstring's reason for it is wrong, and the write-up says 'Narrowings: None'.

Take BLOCK = 2^e <= 2^20 and any n < 2^31. Then n_elements is i32 (triton specialize.cc:281). BLOCK divides 2^31, so cdiv(n, BLOCK)*BLOCK <= 2^31. The largest offset, grid*BLOCK - 1, is therefore at most 2^31 - 1, and block_start is at most 2^31 - BLOCK: nothing overflows. Example: n = 2^31 - 1 with BLOCK = 1024 gives grid = 2^21 and last offset 2^31 - 1, and the mask is false at that offset. The kernel is correct there, but Inst.ok excludes it (Lean: `¬ d1.ok` for this instance). The condition excludes n in (2^31 - BLOCK, 2^31), which is 1023 values at BLOCK = 1024. So the docstring's reason, '(the int32 offsets do not overflow)', does not hold for those n, and docs/examples/vec-add.md 'Narrowings: None' is not exact. This is not blocking: those n are far above the host's use (98432; the benchmark goes up to 2^27), and REVIEWER_GUIDE §2 accepts such bounds. To resolve, either relax the bound to `d.n < 2^31`, or keep it, describe it in the docstring as a simple sufficient bound, and list it under Narrowings in vec-add.md.

*Evidence:* python3: all(((n+b-1)//b)*b-1 < 2**31 for b in powers of two <= 2^20, n in {2^31-1, 2^31-b+1, 2^31-b}) == True
