#### F1

**MODEL_MISMATCH** on `map:148` (blocking): The two tl.multiple_of(…, [16, 16]) hints (src 148-149) are not no-ops: Triton's dry run of the loop body puts them on the pre-loop a_ptrs/b_ptrs definitions, so the compiled loads assume 16-byte-aligned rows. The model drops them, and Inst.ok/Pre allow rows that are not 16-byte aligned.

Why the drop reason `no-op:block-arg-hint` does not hold. visit_For calls `_find_carries(node, liveins, …)` (pinned triton-3.8.0-code-generator.py:1284). `_find_carries` (:465-473) visits the body once as a dry run, with `self.lscope` still holding the values from before the loop, and then erases the dry-run block. During that visit, `tl.multiple_of(a_ptrs, [16, 16])` sees the pre-loop `a_ptrs` (the `tt.addptr` built at line 143) and not a block argument. `semantic.multiple_of` (semantic.py:1775-1779) calls `x.handle.set_attr('tt.divisibility', …)`. `set_attr` takes the defining-op branch (ir.cc:413-414) and writes the attribute on that addptr. The addptr lies outside the erased block, so the attribute stays. The same happens for b_ptrs (line 144). The real visit then also writes the no-op `tt.divisibility_arg<N>` on the scf.for, but that does not undo the first one.

What the attribute does. AxisInfo reads `tt.divisibility` on the op: the hint override at AxisInfo.cpp:1244-1251 and the pessimistic state at :1330-1338. The scf.for iter_arg gets join(init, yield), and the gcd with the `+ BK` step keeps 16. The attribute survives the later passes: TritonToTritonGPU's GenericOpPattern copies op->getAttrs() (lib/Conversion/TritonToTritonGPU/TritonToTritonGPUPass.cpp:33-47 in the 3.8.0 tree), and Combine.td:13-21 copies tt.divisibility when it merges addptr chains. `getAlignment` (lib/Analysis/AxisInfo.cpp:1416-1440) gives min(16 B / 2 B, contiguity BK) = 8 elements along order[0] (the k axis for A, n for B). So the loads in the loop become 16-byte vector or cp.async accesses. The source comment says this was the intent: 'hint to Triton compiler to do proper loop pipelining'. Without the hint, a_ptr comes from inttoptr of a loaded int64, has divisibility 1, and gets 2-byte accesses.

Counterexample inside the claim. G = 1, (BM, BN, BK) = (64, 64, 32) (an autotune config), NUM_SM = 1, M = N = 64, K = 32, lda = 36, ldb = ldc = 64, with a.base, b.base and c.base 16-byte aligned. Gemm.ok and Inst.ok hold (K ≤ lda, M·lda = 2304, (K/BK)·ρ ≈ 8e-6). Pre holds for finite data, and Buf.Valid asks only for 2-byte alignment. Row 1 of the A tile starts at byte a.base + 72 ≡ 8 (mod 16), but the device issues 16-byte accesses there. The result is a misaligned-address fault (or an access the model does not have), not an outcome of the model. So `faithful` is asserted on an instance where it is false. In the same way, any ldb ≢ 0 (mod 8) or a base ≢ 0 (mod 16) breaks the B side or row 0.

What would resolve it, after F-lib below decides the reading:
(1) Write the hints as library checks at the pre-loop definitions of a_ptrs and b_ptrs in `tile`, which is where Triton applies them.
(2) Add the alignment the hints need to Inst.ok/Pre, for example 16 ∣ a.base, 16 ∣ b.base, 8 ∣ lda, 8 ∣ ldb. The host's normal use meets this: torch allocations are 256-byte aligned, lda = K is a multiple of BK, and ldb = N is a multiple of BN.
(3) Replace the map entry [148, 149] with the model text.
If the library keeps the literal reading (see F-lib), the source hint is false along dim 0 and the kernel is undefined behaviour on every input with K ≥ 2. The write-up then has to say so, and the claim cannot stand as is.

#### F2

**LIBRARY_SEMANTICS** on `lib:docs/SEMANTICS.md` (blocking): The library rule 'a hint on a loop-carried variable is a no-op' misses the frontend's dry run of loop bodies. A hint on a carried name before the body reassigns it applies to the value the name holds on loop entry. The library also has no usable reading of a per-dimension divisibility on a dimension of contiguity 1, such as tutorial 08's [16, 16].

Where the rule is stated: SEMANTICS.md:175-181 ('The exception is a hint on a block argument (a loop's induction variable or a loop-carried variable) … it has no effect and the model drops it'). It is repeated in REVIEWER_GUIDE.md:100-105, in the hint section of lean/TVA/Lang/Ops.lean:593-607, and in the drop reason `no-op:block-arg-hint` (REVIEW_PROTOCOL.md:74-76, tools/tvr.py DROPS).

What Triton 3.8.0 does. Both visit_For (code-generator.py:1284) and visit_While (:1131) first call `_find_carries` (:465-501). It dry-visits the body with the pre-loop scope (lscope is not rebound) and erases only the ops the dry run created. So a hint on a carried name, placed before the body reassigns that name, runs `set_attr` on the live-in value:
- If the live-in has a defining op, the attribute lands on that op and is effective (ir.cc:413-414 → AxisInfo.cpp:1244-1251). Through the iter_arg join it also reaches the loop-carried value.
- It is a no-op only if the live-in is a function argument (ir.cc:418-419 skips FuncOp) or a block argument of an enclosing region (`_arg<N>` on that op).
- A hint on the induction variable is a no-op, for a different reason: the dry and real visits bind it to a `ub.poison` placeholder (:1277-1278) whose uses are replaced (:1326).
The rule therefore needs to say what the hinted value is in the dry run, not in the real visit.

Second point, which the fix must also settle. Once such a hint is effective, the library reads `tl.multiple_ofN x [16, 16] contig` as a check on every group start along every dimension. Along dim 0 of a_ptrs Triton's contiguity is 1, so the check requires every element to be 16-byte aligned. AxisInfo itself reads it that way and even applies it globally (include/triton/Analysis/AxisInfo.h:92-100). For a_ptrs this is false at every odd k, and the documentation's 'values in input are all multiples of value' is also false. Under the library's semantics, tutorial 08 is then undefined behaviour on every input. The only consumer in 3.8.0 here, `getAlignment` (lib/Analysis/AxisInfo.cpp:1416-1440: min(div[order0]/elemBytes, contig[order0])), needs only 16-byte-aligned runs along order[0]. The library has to pick one reading:
(a) a consumer-level reading of pointer hints, along order[0], clipped by contiguity;
(b) the literal reading, with such kernels out of scope (an exclusions.md entry).
The bundle fix (the MODEL_MISMATCH on map:148) depends on this choice.

#### F3

**CONDITION_WRONG** on `item:conditions` (blocking): Inst.ok covers block sizes for which the kernel does not compile: BK ∈ {1, 2, 4, 8} (tl.dot needs K ≥ 16 for 16-bit operands), and tiles far beyond shared memory or registers (e.g. BM = BN = BK = 512). On those instances `faithful` is asserted for a launch that fails.

Inst.ok bounds the block sizes only by Triton's block-shape rule: powers of two, at most 2^20 elements per tile. But:
(1) semantic.py:1477-1482 asserts lhs.shape[-1] ≥ min_dot_size[2], and nvidia compiler.py:19-33 returns (1, 1, 16) for 16-bit operands. So BK = 8 (covered: BK = 2^3, BK ∣ K) fails to compile with 'Input shapes should have M >= 1, N >= 1 and K >= 16'.
(2) With BM = BN = BK = 512 (each tile 2^18 elements), the A operand tile alone is 512 KiB of shared memory, above sm_90's 227 KiB. The launch raises OutOfResources ('shared memory', python/triton/compiler/compiler.py:468 in the 3.8.0 tree). BM·BN up to 2^20 also allows a 4 MiB fp32 accumulator per program.
docs/rules/compiler-faithful.md says a failed launch is a `fault` and the rule is accepted only for instances that compile and launch. Launch.Valid does not check either limit.
Resolution: restrict (BM, BN, BK) to what the autotuner can pick, {(128,128,32), (64,64,32), (128,128,64), (64,128,64)} with the default num_warps = 4 and num_stages = 3 (keep NUM_SM free). Alternatively, require 16 ≤ BK and state explicit upper bounds, backed by a compile log of the largest covered configuration on sm_90.

**DOC** on `doc:docs/examples/grouped-gemm.md` (non-blocking): State how weak the tolerance becomes at the large K the conditions allow: errC/S ≈ 0.65 at the largest covered K, and a dropped k-step of nonnegative data is inside the bound from K ≈ 12k (BK = 32).

The table stops at K = 16384, while the Conditions section says K goes 'up to about 1.9·10^6'. At (K/BK)·ρ = 1/2 the bound is (e^{1/2} − 1)·S ≈ 0.65·S. One missing k-step of nonnegative data changes the result by S/T, which is inside errC from K ≈ 8k (BK = 16), 12k (BK = 32), 16k (BK = 64) and about 46k (BK = 128). Examples: K = 16384, BK = 32 gives errC/S = 4.25e-3 against 1/T = 1.95e-3; K = 8192 gives 2.12e-3 against 3.91e-3.
I do not block on this. Post must hold on every covered instance, so a kernel that always drops a step, or rounds the accumulator to fp16 early (about 2^-12·|acc| per step, ≈ 59·ρ at BK = 32), is rejected on small instances. The per-element rate (K·2.4e-7) is within about 6.5x of the tensor core's worst case on another project's measured model (2^-20.68 per k16 step).
Suggest adding the largest-K row and the crossover sentence.

#### F5

**DOC** on `item:spec` (non-blocking): Post's frame does not protect C's padding columns (N ≤ j < ldc), and Inst.ok's C disjointness is per buffer, not per cell. The host never produces either case (ldc = N), so this is not blocking.

Gemm.ok allows ldc > N with c.len = M·ldc. Post's second conjunct fixes only bytes outside every c.bytes. So bytes C[i, j] with N ≤ j < ldc may change according to the spec, although the kernel never writes them, and a user writing into a column slice of a larger output gets no guarantee for the rest of that row. The whole-buffer disjointness of different problems' C also excludes interleaved column slices of one output (C_0 = out[:, :N0], C_1 = out[:, N0:]). group_gemm_fn (line 188) allocates each C as a fresh contiguous (M, N) tensor, so neither case arises from the host. If it is cheap (the proof already shows each program writes only the C cells of its tiles): state the frame over the cells {cAt i j | i < M, j < N} and the disjointness over cells.

*Evidence:* examples/TVAExamples/GroupedGemm/Defs.lean:230-237, 256-261, 316-322; tutorials/08-grouped-gemm.py:188
